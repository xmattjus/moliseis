## Goals / Non-Goals

Goals: retain observable session/navigation and data/error contracts while closing admission and disposal gaps introduced by deferred ordinary actions. Choose a small local coordinator per owner, preserve original runtime object/stack and exactly-once reporting, keep credentials out of observable command state.

Non-goals: OpenSpec 7 editor migration, improve-admin-submission-editor-workflow, repository/backend changes, ObjectBox/Cloudinary/persistence, package upgrades, global infrastructure, canonical spec edits, legacy command deletion, opportunistic cleanup. Any real repository-contract contradiction is a stop/report condition, not permission to expand scope.

## Decisions

### D1 — Synchronous admission and independently owned settlement (F3)

Intent APIs reserve their owner lane before invoking command.run, before any listener can reenter and before action deferral. Rejected requests start no command, overwrite no input slot, alter no snapshots/data, enqueue no work and generate no feedback. bool means admitted, never success. Both refresh Future<void> methods return an already-successfully-completing Future on rejection. Each accepted read returns its OWN Future<void> from a private Completer installed synchronously at admission, before any notify or run. This Future acknowledges safe settlement, not business success; domain/runtime outcomes are observed through snapshots only while live. It never completesError or rethrows an already-handled execution failure. No consumer uses runAsync as admission or settlement. No queue or automatic retry is added.

Use one small feature-private receipt per admitted read (submissions or ignored, public or internal): monotonically unique execution id, exact private Command identity, mutation-generation token if internal, Completer<void>, didStart/entered/actionSettled/settled flags and private terminal classification. Register it as the sole active receipt for that read lane BEFORE any reentrant listener. No credentials, repository payload, widget or callback enters the receipt. The returned Future is exactly this receipt's future; rejected requests cannot obtain/replace it. A next request cannot occupy the lane until the old receipt has safely settled. This is local lifecycle bookkeeping for two reads, not a generic task orchestration system.

Separate observer responsibilities:

| Observer | Lifetime / authority | Responsibility |
|---|---|---|
| public forwarding and completion commits | live VM only; detached synchronously on dispose | cache exposed snapshots, commit lists, notify, advance live post-commit orchestration |
| private results/running settlement observer | installed before run; retained for an admitted execution even after dispose | capture terminal/idle and exact receipt, schedule safe settlement, complete accepted Future once, release private resources |

D3 explicitly gates public unIgnoreSnapshot while post-commit refresh is pending; generic forwarding MUST NOT blindly recopy the private mutation terminal snapshot over that held running snapshot. Private observation first captures terminal identity/outcome before calling any live forwarding that may synchronously dispose/reenter. Its finally/scheduled barrier still executes if public forwarding disappears. Success/Result.error/handled runtime all settle normally after optional live forwarding/commit and the guarded deferred idle boundary; raw failure keeps original object/stack and is reported ONLY by its Command. Do not infer settlement from repository/action Future alone, a first false running notification or a fixed duration. Use the reviewed microtask→event barrier with invalidation/recheck of isRunningSync, receipt identity and action/terminal evidence; do not run a new execution inside upstream's old result/running dispatch/finally. Set settled=true and clear the active receipt/release its lane BEFORE completing its Completer or notifying; all competing terminal/fallback/cleanup callbacks check that same flag. After completing, recheck live owner/token before any follow-up because consumers may run immediately in a later microtask and revoke it. No owner reads its widget after awaits.

| Accepted read lifetime | Settlement contract |
|---|---|
| listener disposes during admission BEFORE command.run | receipt marked skipped, no run/repository call; complete normally once at a private deferred barrier |
| command.run started, dispose BEFORE deferred action entry | retain Command; deferred action checks revoked before I/O and returns existing owner-unavailable expected Result; private terminal observer settles receipt, zero repository calls and no UI failure publication |
| repository pending then dispose | detach public forwarding only; receipt stays pending until physical Command safely settles, then completes normally once |
| success or Result.error after dispose | receipt completes normally once; zero data/snapshot/notification publication |
| handled runtime after dispose | retained Command reports original error/stack once; receipt completes normally once after reporting/dispatch; no second throw/report through Future |
| assertion bypasses normal terminal snapshot | action finally records physical settlement without catching/converting/rethrowing again; private safe-idle fallback classifies abnormal settlement, completes receipt normally once and releases resources; original upstream assertion remains fail-loud in its Zone |
| physical Future never settles | receipt and necessary private Command remain pending/retained; no timeout, synthetic cancellation or false completion |

For assertions, the private receipt classification is abnormal, not Success/Result.error: no fabricated terminal public snapshot, no second global report and no normal continuation to another post-commit read. Internal orchestration consults the private classification AND liveness/token after await; normal-successful completion of Future<void> is not permission to continue. No new catch Object→Result conversion. Action finally is a private physical-settlement witness only; it must not reopen admission, complete a waiter before command dispatch, or start phases.

The existing private façade/cached snapshot/retained cleanup patterns from OpenSpec 1–5 are reused; prior Search receipts/drain and assertion-abort distinction demonstrate private waiter ownership, while ContentSubmission's safe idle forwarding closes reentry. Their write queues and cross-owner persistence obligations are NOT imported: revoked admin reads never start repository work or another phase. Alternative rejected: completion tied to removed public result observer (hanging Futures); immediate completion at dispose (fake cancellation of pending work); runAsync's shared waiter (wrong execution correlation).

### D2 — Auth admission, credentials and authoritative session

requestLogin receives the existing named record, but uses a private no-param Command. Only an admitted attempt installs a one-shot credential slot. Deferred action takes the slot into an action-local variable and clears the field BEFORE the first SDK await. Disposal clears an unconsumed slot; every skipped-entry/failure/terminal path clears remaining references. Credentials exist only as necessary during an admitted SDK sign-in call; no promise of secure zeroization of immutable Dart Strings. No credentials in snapshots, Result values, debugName, diagnostic wrappers, notifications, new logs or errors. debug names are fixed constants. Keep existing expected exception objects/log categories and generic UI copy; never interpolate credentials or log requests/responses. Privacy tests use synthetic sentinel credentials and SDK-shaped errors that contain no credentials, verify all command/global/logging channels and rejected-intent retention.

The shared local phase is idle/login/logout/revoked and is held through the entire attempt, cleanup/restore and safe deferred settlement. `isAuthenticating` means a login/logout reservation exists. `canLogin` and `canLogout` are exactly `!isDisposed && phase == idle` with both private Commands safely idle; they do not infer readiness from currentUser or command snapshot success. requestLogin/requestLogout use that SAME predicate synchronously. Auth events observe the session but never reopen the gate. In particular, an external Admin event can expose the dashboard while local login remains pending: canLogout stays false until that attempt settles. App-scoped Auth outlives its screens; no queue is added.

#### F1 SDK evidence and correlation boundary

The resolved `.dart_tool/package_config.json` and pubspec.lock select gotrue **2.27.2**. Authoritative local sources: `lib/src/types/auth_response.dart:5–16` declares nullable AuthResponse.user, initialized from explicit user or session?.user; `gotrue_client.dart:353–400` saves response.session with `_saveSession` and emits signedIn before returning; `:187–190` exposes currentUser as currentSession?.user and currentSession directly; `_saveSession` at :1458–1462 stores that SAME Session instance. `_signOut` at :1081–1110 logs, captures current token, removes local session, awaits optional storage cleanup, emits signedOut and performs server sign-out with the captured token. There is no identity-conditional/CAS signOut. Public auth events are asynchronously replayed; actual currentSession can already change before our continuation or a notification can reenter application code. Do not depend on receiving every event before checking the client.

Each admitted login has a local attempt id. After `signInWithPassword` returns, use response.user ONLY as correlation evidence, never install it as session/cache or authorize from its metadata. Strong conservative correlation requires non-null response.user with nonempty id, non-null response.session, response.session.user.id equal to response.user.id, and `identical(authClient.currentSession, response.session)` with actual currentUser.id equal to that id. Reference identity is justified by this locked SDK's save/getter implementation; it avoids copying/comparing JWTs and also detects a replaced same-user session. Session/response references stay transient inside the action and never enter Command params/results/snapshots/debug/log data. Any missing/mismatching evidence (including a user-only response or a new same-user Session object) is uncorrelated: return generic expected session-changed/unverifiable Result.error, no signOut and no anonymous restore. This deliberately prefers a conservative login failure to destructive cleanup. Re-audit the correlation guard if SDK semantics ever change; no dependency upgrade is in scope.

CurrentUser alone continues to authorize Admin routing (exists, non-anonymous, appMetadata['admin'] == true). Login command Success requires BOTH demonstrable attempt correlation and a currently authorized Admin. A current B Admin may route to dashboard on its own session event while pending A eventually returns Result.error; these are distinct facts, not contradictory navigation requirements. No failure Result revokes B or overrides the client. A correlated nonadmin A is rejected; cleanup is eligible only for that exact current attempt session and still-nonadmin A.

| Input / current state at final decision | Admission / login result | Cleanup / routing |
|---|---|---|
| login idle / duplicate / conflicting login-logout | idle admits once; all pending conflicts false | one SDK call; no queued signOut or slot replacement |
| response A / same current attempt Session A / current Admin | Success<void> | no cleanup; router follows actual A |
| response A / same current attempt Session A / current nonadmin | access-denied Result.error | eligible for one guarded signOut then live null-session restore |
| response A / current B Admin | session-changed Result.error for A | zero cleanup/restore; B's actual authorization may route dashboard |
| response A / current B nonadmin (A.id != B.id) | session-changed Result.error for A | zero signOut/restore of B; protected access remains denied |
| response user absent, session absent or inconsistent / any current user | unverifiable-session Result.error | no cleanup, no SDK-response-based authorization or false login success |
| response A / different current Session with A.id, null session or anonymous replacement | session-changed Result.error | no cleanup/restore; same id alone is insufficient |
| password Exception | expected failure/log as today | no new cleanup; sync actual session while live |
| event during any pending operation | observe actual client, gate held | route may change; event does not complete/login/logout or enqueue work |
| signOut expected failure leaves real user | access denied for rejected login; logout restore-failed unless final anonymous | log; helper respects any existing session |
| signOut failure after clearance / anonymous restore succeeds | rejected login still denied; logout success | success predicate for logout is actual final anonymous user |
| anonymous AuthException | helper logs; no fabricated session | logout failure if final session not anonymous |
| owner disposed before deferred entry or before cleanup/restore | revoke, clear credential slot, settle privately | no new SDK phase/notify/cache publication |

Before initiating rejected-account cleanup, finish all potentially reentrant application notifications/logging, then recheck liveness, attempt id, response/current Session reference identity, all user ids and current nonadmin status IMMEDIATELY at the signOut call site. No await, VM notify, logger call, event yield or application callback is allowed BETWEEN this final guard and invoking signOut. Recompute the outcome if state changed: correlated current Admin may succeed; otherwise return generic expected session-changed error, without touching the newer session. This covers an auth replacement from a VM listener, even two different nonadmin users, and prevents basing cleanup on B merely because B was current when A completed.

This final client-side guard is an invocation-time check, NOT an atomic compare-and-swap with external auth changes. Once signOut has been invoked, subsequent events/SDK-internal reentrancy or remote changes cannot be cancelled/rolled back by the ViewModel; do not promise stronger guarantees. After its await, recheck owner before any new phase and reread actual currentUser. Start ensureAnonymous only if still null; if B now exists (Admin or nonadmin), preserve it with zero anonymous sign-in. If restore itself is already in flight, its SDK effects may likewise race an external event; the live owner rereads actual state, never installs the captured response. Already-started calls may affect shared session after disposal; the new owner observes actual client events independently. No global session coordinator is added.

Auth business-state forwarding rereads actual GoTrue user/session and only notifies changes in effective session fields, separate from gate/snapshot notifications. Never navigate from login command success. Recheck liveness after every notify; router may unmount screens while Auth remains live. F1 tightens legacy behavior, which ignored AuthResponse entirely; positive test stubs currently returning empty MockAuthResponse MUST be changed to provide an explicit concrete response/session plus independently controllable client state. Do not weaken correlation to satisfy those old stubs.

Preserve observed catch boundaries: expected Exception from signIn/signOut is logged as today; anonymous helper catches AuthException. Unexpected Object/Error remains raw with original stack. Do NOT put anonymous restore in unconditional finally after owner revocation or a raw signOut defect: new phases require a live owner. While live, an unexpected failure terminates the command through existing global reporting, not a fabricated logout Result. This explicitly hardens lifecycle/programming-failure behavior while preserving expected failure outcomes.

### D3 — Dashboard coordinated admission machine

Use local phase normal/mutating/refreshingAfterCommit/revoked plus two read reservations. Admission is synchronous at the façade, not in deferred actions. Read actions only fetch and return domain lists; synchronous result observers commit copies under the live owner and current reservation. Filter state is independent of requests and never becomes a remote parameter. Use ordinary Commands with independent read lanes.

| Phase/reservation | submissions read | ignored read | unIgnore |
|---|---|---|---|
| normal, neither read reserved | admit | admit | admit; reserve exclusive phase immediately |
| normal, submissions reserved | reject duplicate | admit if free | reject |
| normal, ignored reserved | admit if free | reject duplicate | reject |
| normal, both reserved | reject | reject | reject |
| mutating, including deferred entry | reject without starting Command | reject without starting Command | reject duplicate |
| refreshingAfterCommit | internal refresh only | internal refresh only | reject |
| revoked | reject | reject | reject |

Thus a read admitted first excludes mutation until its terminal commit AND deferred release; a mutation admitted first excludes every external read before even its deferred action starts. No pre-commit reads can remain pending when mutation begins, and rejected reads never acquire command-running state. Remove _loadRequest/_ignoredLoadRequest and _refreshingAfterUnIgnore as synchronization authorities; no draining of action Futures is needed. This concretely eliminates the lost-refresh window rather than hoping an old read command has settled.

Mutation command calls unIgnoreSource once and returns Result<AdminEventResolution>. Before I/O, synchronously clear old pendingId on admission (matching observed attempt behavior) with liveness recheck after notify. On expected mutation failure or handled unexpected mutation terminal, release phase after safe settlement, preserve both lists, start no post-commit reads and show existing generic mutation error; a raw mutation failure is reported once by its own Command, never normalized to Result.error.

On successful command terminal, a live synchronous observer stores resolution/pendingId PRIVATELY, reserves refreshingAfterCommit BEFORE notifying or reopening anything, and retains the terminal mutation success privately. Public unignoredPendingId remains null and canOpenPendingSubmission false. Cache the admitted command running snapshot as public unIgnoreSnapshot, with isUnIgnoring true, until both refresh attempts settle (do not synthesize success from a nullable value), matching previous success-feedback timing. The private committed pendingId survives refresh failures but is not yet navigable (intentional F2 hardening). At safe deferred boundary launch exactly one internal ignored-source refresh through the SAME private read Command; after its D1 private receipt has safely settled and the live public observer has committed or retained data, recheck owner/token/private terminal classification before launching exactly one internal submissions refresh. These internal admissions require the same mutation-generation token and bypass only the phase restriction; they do not bypass lane readiness/liveness. External façades never possess that token. Complete even if ignored read returns domain failure or a handled runtime failure. When both attempts settle normally (success, domain or handled runtime failure), atomically publish the original mutation success snapshot AND public unignoredPendingId from the private committed resolution, release exclusive phase at the safe boundary and notify once. canOpenPendingSubmission is exactly live owner, normal phase, completed successful unIgnoreSnapshot and non-null public unignoredPendingId. No observer sees link-ready with logical mutation still running. Assertion-abort or owner revocation never grants readiness or launches further refreshes. Read snapshots retain their independent failures; never promote refresh failure to mutation failure or rerun remote mutation automatically.

The orchestrator runs from terminal observers/barriers, not a second async action wrapping/rethrowing the first command's failure. Read raw failure is reported once by its own command; it is visible through unexpectedError/hasFailure and does not get rethrown through unIgnore. Assertion failures remain fail-loud and are outside normal continuation guarantees. Revoke all follow-ups on dispose. No zero-duration sleep polling, new generic scheduler or new command lane.

| Event | Data/result and next phase |
|---|---|
| external refresh rejected during mutation | snapshots/lists unchanged; post-commit obligation unaffected |
| mutation pending | both private committed and public pendingId cleared for this attempt; no link |
| mutation success / ignored refresh pending | preserve resolution/pendingId privately, public id null and link unavailable; ignored then main refresh once |
| ignored refresh settled / main pending | private resolution retained; public id null, link unavailable and unIgnore logically running |
| both refresh attempts normally settled | original mutation success and public pendingId published together; link enabled only if returned id non-null |
| ignored refresh fails | retain ignored data/error/private pendingId; still attempt main, link remains unavailable until main settles |
| main refresh fails | retain main data/error and successful ignored commit; expose link at joint settlement if pendingId exists |
| both refresh fail | mutation still success; expose retained pendingId/link only at joint settlement; user retries reads |
| filter changes in any live phase | local selection only; no stale selection captured by read; ignored selection requests read through façade, rejected during exclusive phase; mandatory post-commit read still runs |
| open returned pending | only after canOpenPendingSubmission; user-triggered push, never automatic; recheck current owner/id/readiness before push |
| dispose before remote mutation commit | already-started mutation may commit remotely, zero local publication or refresh |
| dispose after commit, either refresh pending | public id remains null, snapshots freeze; accepted read receipt still settles privately; no next read/link publication/navigation |

Alternatives rejected: latest-intent reads (unnecessary replacement semantics); action-time running flags (deferred admission race); old Future drains (not command settlement); direct repository post-commit reads plus parallel custom loading state (duplicate execution/error plumbing); busy requests represented as Result.error snapshots (would overwrite relevant execution/feedback); returning refresh error as mutation failure (would invite duplicate mutation and violate current UI).

### D4 — Consumers, notifications and ownership

AdminLoginScreen validates/trim email as today and calls requestLogin; observes VM plus loginSnapshot and isAuthenticating to disable sign-in during either auth operation. Generic login failure uses hasFailure, never upstream isSuccess or raw error.toString. Bind/unbind the session listener in initState/didUpdateWidget/dispose, including owner changes at identical route. Capture owner and router before callbacks; guard mounted and owner identity on queued work. Its existing pushed-route replacement remains session-driven, route-checked and at-most-once per route/owner transition. Router handles declarative redirects; no success callback adds another push/go. Repeated auth event plus command completion cannot replace twice.

Dashboard observes its own VM cached snapshots and the application Auth owner for logout availability; no direct Command merging. All menu/pull/retry/filter/editor-return invocations use façades. Pull-to-refresh awaits the accepted read's completion; rejected read resolves without changing error state. canUnIgnore includes both read reservations and exclusive phase; isUnIgnoring includes refresh. Status filters do not load. Selecting ignored requests its read. Initial route create calls refreshSubmissions exactly once, never from build. A true editor result calls refreshAfterEditorChange once after mounted, captured Dashboard owner, !isDisposed and widget/Provider identity checks. The ViewModel owns subsequent submissions/ignored coordination even if the widget unmounts after registration; the callback performs no later widget/context access. Preserve no invalidation on false/null or obsolete editor return. See F5 below for the explicit guarantee under busy admission. Pending editor link is explicit and hidden until canOpenPendingSubmission becomes true at joint post-commit settlement; that same returned id and refresh-on-return behavior are retained even if either/both reads failed. Capture owner/id before navigation, and recheck mounted/current owner/readiness/id immediately before push; an obsolete retained callback after a new mutation or dispose cannot open the old revision. No post-await link publication comes from the widget.

F4 visual contract: rebuild Dashboard header actions with a ListenableBuilder on the current Auth owner, rebinding automatically when widget.authViewModel changes. Render Logout disabled exactly when canLogout is false. The existing shared ResponsiveOverflowMenu/MenuItem cannot express disabled callbacks (MenuItem.onPressed is non-nullable and there is no enabled flag); do not invent an API or broaden shared widget scope. In this Dashboard only, replace that use with a small local responsive actions builder using the SAME `context.windowSizeClass.isCompact` decision: compact MenuAnchor/MenuItemButton and wide Row/IconButton, with Logout.onPressed = canLogout ? guardedLogoutCallback : null. Preserve refresh action, icons, copy, tooltip, overflow affordance and compact/wide behavior. No new reusable component/module, package, or change to ResponsiveOverflowMenu is required. The limited local two-action layout is preferred to a shared API change for this one required consumer.

For logout capture Auth owner, Dashboard owner, router and current route/owner generation before requesting admission. A stale callback first checks mounted/current owner identity, then always calls requestLogout as the definitive synchronous gate even if it rendered enabled earlier. On false, return with zero local navigation, signOut calls or success feedback. On true, recheck mounted/current captured owner and that routing still represents the originating dashboard (an admission notify can synchronously redirect/unmount); only then call captured router.go(Home) ONCE. ### D5 — Disposal and errors

Auth application owner: synchronously mark revoked, clear pending credential slot, stop accepting/forwarding, cancel auth subscription, detach ONLY public command results/running forwarders. Dashboard route owner: revoke generation, block filters/intents/commits and navigation readiness, detach ONLY public observers and disable further orchestration. D1 private results/running observers and per-execution receipt remain registered until a run already started safely settles, including pre-entry no-I/O execution and late success/domain/raw failure. Disposal MUST NOT call Command.dispose while it has admitted/deferred/physical work, remove its private observer, complete a pending repository receipt early, or leave a public refresh Future dependent on detached forwarding. Idle/never-run commands release once. Private settlement must precede observer removal/Command disposal; notifier disposal is scheduled outside synchronous VM dispatch as in approved ordinary owners. Do not reuse a Command on its transient first sync-idle notification. Do not catch Object to return Result.error; no broad wrapping for telemetry. Result.error remains expected and uses existing UI retry/logging; raw StateError/TypeError retains object/stack and one global report even after owner disposal while command is privately retained. ## Independent code review remediation F5 — editor-change invalidation

### Evidence and revised API

The reviewed `_openEditor` awaited two ordinary refresh façades. Both return an already-completing Future on rejected admission. A manual submissions read admitted before editor save, or exclusive unIgnore, could therefore reject the post-save read and leave only stale data. Waiting for that rejection did not register any future work. This is a real lost-demand bug, not a defect in the ordinary single-flight policy. F1–F4 remain unchanged.

`Future<void> refreshAfterEditorChange()` now registers an owner-local monotonically increasing revision and its completion waiter synchronously, before scheduling or notifications. It is a separate invalidation API, not an admission override/force boolean. Ordinary refreshSubmissions/refreshIgnoredSources still reject without queueing. No new Command, repository, shared scheduler or global state exists. Proposal impact already covers Dashboard refresh ownership and its existing production/test surfaces, so proposal.md needs no change.

### Freshness and transitions

Every acknowledged live editor revision must be covered by a submissions receipt admitted AFTER that revision, provided the owner remains active and blocking work terminates. Receipt completion from before the revision never counts. At main admission capture the highest pending revision BEFORE `_startSubmissions` can notify reentrantly. All waiters through that revision form one batch. Once admitted, finish that batch's main and optional ignored phase, complete only its waiters, then admit another main for any newer revisions. This avoids requiring a quiet stream of events before older callers can complete.

| State/event | Action / retained demand |
|---|---|
| Live registration, idle lanes | Save revision+waiter, schedule one drain microtask; admit one main receipt for all revisions waiting before admission |
| Main already reserved, including before deferred action | Retain marker; old safe settlement wakes drain and admits a distinct new main |
| unIgnore mutating/first internal read/second internal read | Retain marker, no external read; preserve internal ignored→main order and F2 publication; drain admits fresh main only after exclusive release |
| New event during editor-owned main | Current batch finishes for its captured revision; newer waiter requires another main admission after the new event |
| Main safely settles normally | Evaluate current showIgnored, never a pre-await selection; false completes batch, true establishes its ignored demand |
| Ignored demand, ignored lane busy | Retain phase; unrelated ignored receipt does not count; admit fresh ignored when it safely releases and exclusivity permits |
| New event during editor-owned ignored | Finish current ignored receipt and only current batch; next batch admits fresh main and evaluates current selection afterward |
| Filter changes while waiting | No filter restoration/remote filter parameter; ignored necessity decided after batch main settlement; once established its demand survives a busy ignored lane, even if selection changes again |
| Domain or handled raw terminal | Physical receipt safely settles; process obligation once, retain existing failure data policy, never auto-retry or rethrow/report child error |
| Main assertion-abort | Preserve original fail-loud assertion; privately settle batch acknowledgement without ordinary ignored continuation or fabricated terminal; any newer explicit revision is a separate batch |
| Dispose before tick/during either read/waiting exclusive | Revoke, clear coordinator pointers and complete all local coordinator waiters normally once; no next read/publication; existing physical receipts retain D1/D5 |

### Wakeup and reentrancy boundary

Only registration, safe read settlement and safe unIgnore release/abort schedule the drain. Existing `_AdminExecution.settled` is set at its revision-checked microtask→event terminal barrier, with its physical Completer resolved before the drain can observe it. No first idle notification, repository completion, timer, polling or notifyListeners-only trigger satisfies a revision. `_editorDrainQueued` coalesces wakes; every wake advances at most one admission and stops immediately when its receipt/phase is blocked. Admission still reserves before public notification. Reentrant changes after capture remain pending for a later batch; they cannot overwrite the captured revision or reopen a lane inside old upstream finally work.

The small waiter list stores only revision+Completer, never queued repository operations or payloads. Coordinator waiters and physical read receipts have different contracts: dispose completes the former immediately, while a physical nonterminating receipt stays retained/pending. Live coordination may remain pending if required work never terminates; revocation cannot leave a local coordinator orphan. A widget removed after successful registration does not revoke a still-live Dashboard owner. A widget/owner replaced before editor return cannot register at all.
