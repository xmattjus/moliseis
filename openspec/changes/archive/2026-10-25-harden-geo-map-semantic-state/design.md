## Goals

One semantic source of truth; deterministic target-bound data; fetch-only async actions and synchronous authoritative commits; complete navigation/lifecycle regression coverage using existing Provider architecture and Result pattern.

## Non-Goals

No second execution policy, global Command migration, physical Future cancellation, generic cache/state container, Search repository/history refactor, filter concurrency redesign, backend/dependency changes or URI encoding of transient selections. Existing unrelated legacy commands stay intact; new APIs never depend on their deprecated types.

## Decisions

### 1. Mode, identity and selection intent have distinct responsibilities

Planned addition `lib/ui/geo_map/view_models/geo_map_mode.dart` defines a value identity record `GeoMapContentIdentity = ({int id, ContentType type})` and immutable sealed GeoMapMode variants named GeoMapExplore, GeoMapSearchResults(query), GeoMapPostDetail(identity). Only positive remote IDs and Event/Place types are admitted. Mode is VM-owned authoritative presentation; intent is an ephemeral command parameter, never a second stored semantic state.

Retain `GeoMapSelectionIntent` and the single `selectContent` lane. Convert complete route identity to existing EventSelection/PlaceSelection at admission. `requestSelection(intent)` handles ClearSelection synchronously through Explore transition, without running an artificial clearing fetch. Event/Place admissions establish PostDetail, clear resolvedContent, invalidate old Nearby target, then call `selectContent.run(intent)` and notify once after all coupled fields are coherent. No new showEvent/showPlace migration.

`resolvedContent != null` implies PostDetail and exact remoteId plus runtime Event/Place type match. Every accepted semantic admission creates a fresh immutable mode instance, including equal-value local intents; successful resolution retains the exact PostDetail instance created at request admission. Synchronous `showExplore(anchor)`, `showSearchResults(validQuery)` and `showContent(materialized)` update every coupled field before one VM notification. Explore camera settle updates the anchor while retaining the same Explore mode instance, so it does not repeat entry presentation. `showContent` revokes pending lookup and commits identity/data together, with no I/O even for equal identities. It is a new intent; equal route rebuild is not. Search query validity is checked by the screen using the unchanged Search predicate before admission; the VM transition also rejects invalid input rather than exposing an invalid mode.

`exploreAnchor` is initialized to the existing Campobasso center. It changes only on accepted Explore settle or explicit/default/failure return to Explore using live camera center. Selecting a Post never overwrites that remembered anchor.

### 2. Fetch/commit separation replaces redundant counters

Selection, Nearby and three migrated Weather actions only retrieve/compute immutable request-local `Result<T>` values. They capture use-case/API dependencies, not live State or mutable VM fields, and perform no VM mutation after await. Register synchronous completion observers before any view observer. Observers commit only authoritative terminal snapshots while live, with semantic target checks described below. Remove observers before disposing restartable owners and before `super.dispose()`; retain existing guards on unrelated legacy actions.

Foundation execution ownership already prevents obsolete terminals reaching the observer. Do not add per-action request generation counters. Additional guards are limited to independent semantic target checks, screen effects and lifecycle; they address gaps outside command ownership. New ordinary actions, if actually needed, use ResultCommand factories; this change adds no ordinary child disposal policy.

Preserve raw runtime throws, original error/stack global reporting including stale handled throws, expected Result.error without automatic telemetry, and upstream fail-loud assertions. Do not catch Object and fabricate a domain error. In command_it 9.5.2, disposing an in-flight ordinary child can break late-throw reporting; use unchanged RestartableCommand deferred settled-child retirement, never manually dispose its children or eagerly dispose a raw live child.

### 3. Post terminal error ordering, camera-aligned fallback and feedback

Fetch validates identity with existing intent.matchesPayload before returning success; wrong ID/type becomes operation-specific GeoMapSelectionIdentityException defined in the existing selection-intent file. Preserve expected repository exceptions and raw handled runtime failures separately. AssertionError stays fail-loud without not-found fallback.

The VM's first completion observer commits matching success only, retaining its existing final matchesPayload guard even though normal fetch validates. Screen also rejects malformed public terminal success snapshots (wrong type/null fault injection used by existing regression tests); these are contract rejections, never valid content or automatic retries. For terminal failure it leaves PostDetail with absent resolvedContent and the terminal snapshot intact. Screen's synchronous terminal observer reads the actual MapController.camera.center (before map readiness, use existing initial center) and calls VM `fallbackToExplore(anchor, snapshot)`. That method accepts only the still-current terminal failure (or rejected malformed terminal success) for the current Post identity and live owner, with absent resolvedContent and selectContent.isRunningSync.value == false. It constructs a fresh Explore object, commits Explore/anchor/Nearby target together, then notifies once and returns that locally captured object, never a reread of mode after notification. It MUST NOT run ClearSelection or invalidate selectContent. Screen coordinates the camera-derived input; VM still owns the atomic semantic transition. No VM callback reads widget/controllers, no extra remembered fallback state and no automatic camera recentering.

Screen’s command observer handles failures/contract rejections only and consumes each terminal snapshot once by object identity. It verifies owner, matching current Post mode, absent resolvedContent, command snapshot identity and !isRunningSync.value before fallback. After notify returns, it requires identical(currentMode, returnedExplore), the same terminal snapshot, live owner and no newer running admission before capturing the resulting effect token and scheduling one existing “Contenuto non trovato” feedback. Recheck these guards at feedback execution. Even equal-value reentrant intent replaces the mode object and prevents obsolete feedback. Success presentation belongs solely to the mode/materialization observer in section 9; no separate command-success effect path. Stale failures and assertions never cause fallback/feedback.

Explore invariant: after initial entry, explicit/default return, failure fallback or accepted settled navigation, committed exploreAnchor equals the camera center used for that transition, and Explore Nearby target is derived from that anchor. During a gesture/debounce only the last committed anchor is authoritative. Failure at camera B commits B immediately and cancels old settle callbacks; movement continuing after fallback schedules a newer settle and replaces B. Once settled, camera/anchor/Nearby coordinates agree. Unit tests exercise fallbackToExplore with a supplied anchor; screen tests read the real camera and prove no automatic movement or unrelated-anchor results.

### 4. Route identity is an event keyed by identity AND owner

`GeoMapScreen.routeSelection` is one nullable complete value identity. Router keeps RouteParameters.contentId/contentType parsing; partial, invalid or absent pairs map to null, preserving default-map fallback and query URI policy. On init and on identity-by-value OR GeoMapViewModel instance change, reapply selection. Equal identity/equal owner does nothing, pending or settled, including after local dismissal and unrelated Sync/AdminAuth refresh.

Route lifecycle preparation MUST NOT notify an ancestor Provider from initState/didUpdateWidget. prepareRouteAdmission(identity, liveCameraCenter) immediately installs a fresh authoritative mode and coherently clears resolved content/committed Nearby terminal, updates the Explore anchor only for a default route, and invalidates obsolete selection/Nearby publication without ViewModel notification or I/O. Screen immediately clears its Search fence, invalidates Map Search and clears the Weather target. The same-frame Screen build therefore reads the new VM mode and never renders old Post/Search/Nearby data; there is no parallel Screen mode. Command isRunningSync remains a synchronous coordination API, not a UI Listenable; touched UI consumers observe deferred results and read logical running only as an admission predicate. This prevents route-time invalidation from synchronously marking UI builders during build while preserving immediate publication revocation and foundation behavior.

Screen schedules admitPreparedRoute(exactMode) after frame using the existing effect token, captured owner, complete route identity and exact prepared mode. It publishes the semantic notification and, for Post, starts the existing lookup without replacing the prepared mode. Recheck lifecycle/owner/token/route/mode before controller access or admission; same-frame A→B→A preparations have distinct mode/token ownership, so the first A cannot regain authority. Local marker/Search/close transitions stay synchronous and replace the exact mode/token, superseding queued route admission. A new owner already in correct default Explore needs neither preparation nor deferred notification/lookup. Equal route/equal owner does nothing, including after local dismissal; changed owner initializes the current URI. On replacement detach old observers and revoke old-owner commands; Provider retains GeoMap/Search disposal ownership. Removed/invalid route prepares Explore at live camera and revokes pending work immediately; its extent 0.3 is scheduled safely after frame. Preserve shell/branch keys, restoration identifiers, route-owned Back/predictive Back and root full-screen Gallery.

Retain current Weather owner creation in router and Screen disposal on replacement/unmount. Owner replacement may occur even on unchanged Map URI during refresh: the current forecast button initializes the new owner for retained content without another GeoMap lookup. Do not redesign DI lifetime.

### 5. Search integration reuses completed migration

GeoMap does not depend on SearchViewModel. Screen checks `SearchViewModel.isSearchQueryValid` exactly as implemented (query.length >= 3, no new trimming/ranking). One Screen admission path handles valid submit AND Map retry; the wrapper never calls loadResults.run directly. Capture both VM owners and loadResults.results.value immediately before the semantic transition. showSearchResults returns its locally created fresh SearchResults mode object after notifying (not a reread of current mode). Only if mounted, both owners still match and that exact object remains current, install one Screen-local presentation fence `(searchOwner, mode, excludedSnapshot)` and call `loadResults.run(query)` in the same event. Do not overwrite the fence after run: synchronous running listeners can reenter admission. A reentrant mode change during notify aborts the outer admission. Close only the still-current open search popup with the same guards; the sole presentation observer schedules sheet 1.0. Mode commit invalidates Post and Nearby.

The Map-specific GeoMapModalSearchResults wrapper receives the fence, GeoMapViewModel owner and guarded result/retry callbacks through the existing sheet composition. Read the owner’s live mode directly rather than treating a cached widget query as authority. It observes GeoMapViewModel and deferred results, and reads isRunningSync only as a coordination predicate; read one current snapshot. Show the unchanged shared SearchResultSliverList only when the fence's owner and exact immutable mode are current, the snapshot is NOT identical to excludedSnapshot, paramData equals the mode query, logical running is false and the public snapshot is terminal (completed or hasFailure). Otherwise render the existing skeleton; neutral/loading never expose retained results. An admitted failure lets the shared child render its existing error/retry, never a collection. SearchViewModel's already-registered first observer commits the successful collection before rendering; keep it and the shared child unchanged. This fence stores one prior snapshot reference, no copied collection, accepted-terminal cache, request counter or generic execution abstraction.

Why both windows are covered: run updates isRunningSync synchronously while the old terminal may still be public; that exact old snapshot is excluded even for the same query. Loading publication has a different snapshot but remains nonterminal. When logical running later becomes false before terminal publication, the public snapshot is either the excluded pre-admission snapshot or a loading/neutral snapshot, so still cannot render a collection. The new authoritative terminal is a different snapshot and is admitted immediately on its public notification, including repeated equal queries. Compare snapshot/mode by identical, not CommandResult value equality; foundation creates new execution snapshots and owns subsequent publications.

Clear the fence on leaving its exact Search mode, either VM owner replacement and Screen disposal, before obsolete callbacks can act. Retrying or submitting equal A creates a fresh mode/fence and captures whatever snapshot is public at that admission. A retained wrapper’s result/retry callback rechecks the same live fence, exact mode/owner and snapshot admission predicate before selecting content or resubmitting; it cannot reopen an obsolete surface. Replacing Search owner while the same GeoMap Search mode is retained shows skeleton immediately and schedules that valid query once through this admission path after frame, guarded by the captured mode/owners and existing effect token. Equal owner/mode rebuilds do not submit; a GeoMap owner replacement follows route semantics first. No new listener or callback may survive owner replacement/unmount.

Invalid Map submit is rejected before both mode and result-lane admission: retain the current mode and its matching result snapshot. Forwarding a short query while retaining SearchResults(A) would replace A's snapshot with a no-op for another query and strand its presentation, so Map must not do that. Foundation short-query invalidation/no-op semantics remain unchanged for existing Search callers and suggestion edits; no Search VM behavior changes. No duplicate Search primitive tests or VM migration. Result selection calls showContent with the existing object, invalidating pending Post and entering materialized PostDetail. Explore/Post transitions invalidate pending Map result loading so hidden late results do not become an active surface; suggestions keep the existing independent popup lifecycle/invalidation.

### 6. Nearby has one derived target and one committed terminal snapshot

Define two operation-specific record typedefs in existing geo_map_view_model.dart, not new files or sealed hierarchies:

- `GeoMapNearbyTarget = ({GeoMapContentIdentity? post, double latitude, double longitude})`; null post tags Explore, a complete post identity tags Post.
- `GeoMapNearbyOutcome = ({List<ContentBase> items, Exception? firstError})`, with an unmodifiable request-local list.

`nearbyTarget` is derived from mode plus exploreAnchor or matching resolvedContent. Search/unresolved Post yield null. Do not store another requested target; compare old/new derived values during semantic commits to invalidate the one lane and clear its sole committed terminal snapshot. Expose a read-only nearbyTerminal getter; outcome and nearContent derive from its successful aggregate payload, not independently stored collection/error flags. Explore anchor remains unchanged while Post is active. Different identities at equal coordinates still differ as targets.

One RestartableCommand<GeoMapNearbyTarget, GeoMapNearbyOutcome> fits mutually exclusive Explore/Post sheets. `requestNearby(target)` accepts only target == current derived nearbyTarget. Reject invalid coordinates using the existing LatLng.isValid predicate before I/O. Same target with current immediate running state or committed terminal snapshot is reused; explicit retry clears the committed terminal before starting a fresh intent. Never reuse raw results.value after synchronous invalidation: its old terminal can remain until the deferred neutral turn. Target null→same value after leaving a surface is new work because invalidation cleared its committed terminal. Deferred initial widget callbacks never retarget the VM.

Fetch calls Places then Events through unchanged GeoMapUseCase/repository coordinate queries, accumulates locally and retains the original Places error if present else Events error. Return Result.success(outcome) for a completed aggregate even with expected partial/total discovery failure: outer success denotes completed aggregation, not fully successful discovery. Only firstError == null is full discovery success. An unexpected throw remains the outer command runtime failure; no partial publication after such a throw is promised. The first live authoritative observer atomically stores the terminal CommandResult snapshot, including successful aggregates or raw runtime errors, only for the current target and non-running logical lane. Read the stored snapshot once for each presentation projection. Clear it synchronously on target change/retry; it prevents stale A snapshots during A→B→A and represents raw failures without another failure field. No mutation occurs inside awaited fetch.

### 7. Nearby shared widget takes one coherent presentation projection

Define a small UI record typedef next to NearbyContentHorizontalList: `NearbyContentPresentation = ({bool pending, List<ContentBase> items, Object? error})`. It is a projection, not a command class or generic adapter. Replace deprecated Command1 parameters/imports in both shared widgets with four required load inputs: `Listenable loadListenable`, value `Object loadKey`, `VoidCallback onLoad`, `NearbyContentPresentation Function() readState`; add only nullable `VoidCallback onRetry` for GeoMap's actual retry consumer. Existing item-tap/layout inputs remain.

readState is evaluated once inside ListenableBuilder so items, error and pending are coherent and replacement collections are fresh without a parent rebuild. Neutral and running both project pending=true and skeleton; completed empty is pending=false, items empty, error null and alone permits the existing empty message. Completed items/error distinguish full list, partial list with error, and empty terminal failure. Error is original firstError or unexpected runtime Object. Pending always hides items/error. There are no separate isLoading/hasFailure/readItems/partial-error callbacks.

loadKey is (owner, semantic target) by value; widget coalesces initial/changed-key post-frame load and checks mounted/current key before calling onLoad. GeoMap callback additionally checks current derived target at VM admission. readState captures the committed terminal once: target mismatch or absent terminal maps to pending, completed aggregate projects its items/firstError, and terminal unexpected error projects pending=false, empty items and the original runtime Object. A missing successful outcome on a runtime terminal must never become an indefinite skeleton. This covers the synchronous interval before deferred neutral/running snapshots. Retry clears/hides the prior terminal then starts current target again; partial failure presents list plus existing localized error text and retry, total failure error/retry. No unrelated Nearby layout redesign.

Normal PostScreen passes its existing command as Listenable and closures mapping existing idle/running to pending, completed to its current nearContent, and error to empty items/original error. onRetry is null to preserve existing normal Post error presentation. The normal Post onLoad closure and GeoMap requestNearby preserve the existing coordinates.isValid admission guard now removed from the shared widget API; invalid coordinates cause no repository call and never imply completed-empty success. The call site uses its already-existing legacy VM fields but introduces no deprecated type/import/contract. PostViewModel remains unchanged with event-first ordering, original partial/error semantics and NAV-07 ownership. PostSectionNearbyContent only forwards this coherent projection; no new adapter hierarchy or utility infrastructure.

### 8. Weather has one target writer per surface; widgets only request

Define `WeatherTarget = ({int id, ContentType type, double latitude, double longitude})` beside WeatherViewModel in its existing file. VM owns nullable currentTarget. Its synchronous `setTarget(target)` is idempotent by value; a changed/null target immediately invalidates all three lanes, resets current unknown defaults and clears hourly/daily data. No target generation counter or new target file.

Only the containing screen binds target from its authoritative content source:

- GeoMapScreen binds a synchronous GeoMapViewModel listener on init/update. Derive target from matching PostDetail/resolvedContent, else null. Each semantic notification/rebinding updates Weather before a later Button callback can run. Routed and materialized local selections share this path.
- Ordinary PostScreen observes the existing loadEvent or loadPlace command selected by its isEvent input (existing commands are Listenable); only terminal completed load of that selected command permits reading the late content field. On init inspect completed state, on terminal/update derive target from content; on replacement detach old listeners, bind new source/Weather owner and apply current target. Do not change PostViewModel or its concurrency policy.
- Screen owner replacement clears old target before disposing/releasing old ownership and sets new owner from the current source. Screens do not start forecast I/O. During build/unmount, setTarget performs only synchronous fields/command invalidation: it does not notify VM listeners synchronously. Existing command results publish their deferred neutral snapshots and rebuild target-gated consumers safely.

WeatherForecastButton NEVER calls setTarget. It requests current weather only through VM `requestCurrent(expectedTarget)`; matching hourly/daily request methods use the same contract. Each method checks live owner and expectedTarget == currentTarget before any lane action, so mounted obsolete Button/modal callbacks cannot reassert A, invalidate B or restart obsolete work. Same-current-target initial/current request deduplicates against immediate isRunningSync and current lane snapshot; an explicit retry bypasses completed/failure reuse but still checks target. Because invalidation snapshots are deferred, maintain no historical submitted tuple as authority: coalesced post-frame Button admission rechecks target and lane state after the invalidation turn. A neutral lane initializes even on A→B→A or A→null→A; terminal failure does not auto-retry.

Migrate exactly three lanes to existing RestartableCommand<WeatherTarget, ForecastData>; fetch only calls unchanged CachedWeatherApiClient and returns Result; matching synchronous commits retain the current mapper projections. Authoritative synchronous observers commit only matching currentTarget. Current is initialized by Button on init, owner/target update or neutral-lane observation; equal owner/target rebuild admits nothing. It removes occupied-command waiter machinery. Hourly/daily remain lazy on modal open; retry is lane-specific and target-checked. Preserve cache behavior (admission counts differ from API calls), initial unknown/disabled presentation and current existing failure presentation; add no unrelated current-weather retry UX. No blanket forecast-on-screen or global Weather migration.

Disposal sets existing disposed flag, removes completion observers, disposes restartable wrappers then super.dispose, with NO notifyListeners during teardown. No eager disposal of running ordinary child. The owning screen detaches content-source listeners before owner disposal. Expose read-only isDisposed for guarded UI requests/builds, not as observable semantic state.

Button owns at most one outstanding Weather modal, including establishment and exit transition. Keep one nullable opening token in its State, plus the cancellation closure for that opening; no route registry or new helper hierarchy. Add only an optional `void Function(ModalBottomSheetRoute<T>)? onRouteCreated` parameter to existing appShowModalBottomSheet: construct its existing route in a local variable, invoke this capture-only callback synchronously before navigator.push, and retain its existing Future/default behavior for every other caller. Button captures that exact route and the matching Navigator synchronously; a route popped before its builder runs still has an observable completed Future. This narrow handle is required because the existing push Future completes before exit removal and builder-only capture may never occur. At onPressed entry recheck mounted, captured owner/target against current widget and VM binding, and current forecast readiness. If a token already exists, return without forecast requests or navigation. Otherwise synchronously assign a fresh Object token BEFORE either lazy hourly/daily request or appShowModalBottomSheet call. Install its cancellation closure immediately; capture content/owner/target and opening-local revoked flag, route and navigator references. Only the accepted opening requests hourly/daily through the existing target-checked methods. Recheck binding/revocation before push in case synchronous request coordination reenters a target change. Rejected or stale opening callbacks perform neither requests nor a push.

The builder uses the opening’s captured route/owner/target and performs no admission changes. Cancellation on Button target/owner change or removal marks that opening revoked immediately, even before its builder executes; the existing current-results observer also cancels an outstanding opening on neutral invalidation, covering A→B→A before widget rebinding. A builder discovering a disposed owner or mismatching current binding invokes the same opening-local cancellation and renders no forecast; do NOT clear admission at cancellation. A revoked opening renders no forecast even if A→B→A makes the target value equal again. When its route is known, schedule guarded after-frame dismissal using only captured local references: if navigator is mounted and that exact route is still active, pop if current, otherwise remove that exact route. Never pop a newer/parent route. Cancellation is idempotent and schedules exact-route dismissal once the captured route has been pushed; it never waits for builder execution. If cancellation happens during lazy request coordination before push, abort push and release that unpushed admission in finally. No deferred dismissal reads State/widget/context. No automatic replacement modal is opened for B while A closes.

Release admission in the opening’s try/finally only after a successful synchronous push’s appShowModalBottomSheet Future settles AND its captured TransitionRoute.completed Future finishes removal/exit animation. Set a local pushed flag only after the helper successfully returns its Future; a synchronous pre-push failure/aborted opening must not await an uninstalled route’s completed Future. Flutter's Navigator.push Future can complete at pop before the modal is fully closed; that alone must not unlock admission. Synchronous push failure also reaches finally and unlocks the still-owned token without hiding the failure. Before touching State in finally, check mounted; clear token/cancellation closure only if identical(currentToken, capturedToken), with no old callback modifying a newer opening. Normal reopening is allowed after full close and only through a fresh valid admission. Dispose invokes the locally captured cancellation closure, detaches/clears State ownership, then disposes normally; later finally does no State/context/controller access after its mounted guard, and local dismissal checks navigator lifetime independently. Late old dismissal/completion callbacks can neither clear a newer token nor affect its route. No disposal-time VM notification or global manager is required.

Modal receives expectedTarget and captured content/owner. It observes all three results, gates title/current/hourly/daily by live owner/target and matching snapshots, and performs no target writes. Target change emits neutral snapshots which immediately gate old data; close follows Button lifetime. Hourly scroll callbacks capture owner/target/data and check mounted/attachment/current equality; no extra scroll generation. All modal/forecast listeners detach normally on removal. Tests must exercise target change without Button rebuilding until after invalidation, owner replacement during build and screen removal with modal active.

### 9. Camera and one-shot effects remain local

Screen owns camera/controllers and one local UI-effect token shared by deferred route/camera/sheet/feedback operations. One synchronous mode/materialization observer owns all entry presentation, for routed and local content alike. It keeps only a last-observed pair of mode reference and resolvedContent reference for effect deduplication; unrelated event/place/filter/Nearby notifications leave that pair and token unchanged. On pair change, record the pair and rotate the token before scheduling effects. New Explore/Search mode schedules its entry extent; unresolved Post schedules no centering, and newly resolved/materialized Post schedules one existing center/sheet effect. Anchor-only Explore updates retain the mode reference and schedule no entry animation. Rebind/reset the pair and rotate the token on GeoMap owner replacement; deferred route admission and disposal also revoke prior effects. All effects check the captured exact mode object by identical, and Post effects additionally require identical resolved materialization and !selectContent.isRunningSync.value. An equal-value reentrant intent therefore invalidates old effects without another semantic revision. The pair is incidental effect dedupe, never rendering authority; no per-lane async counters.

Retain a cancellable 1500ms Debounced object, with a synchronous settle function that reads current camera at execution time and commits only when mounted, same owner/token and Explore. Cancel on movement start, semantic transition, programmatic presentation move, owner replacement and disposal. Because no async work occurs after the debounce function begins, cancellation plus current owner/mode/token checks suffices: remove separate movement revision and captured-center await continuation. Latest end schedules a new settle. Explicit/default/failure Explore entry cancels old settle and commits actual current camera immediately; no remembered-anchor camera restoration.

At GeoMap's existing MoveStart/MoveEnd/FlingAnimationEnd callback boundary ignore source==MapEventSource.mapController for Explore navigation; this is the only programmatic movement used by current Post presentation (_mapController.move). Keep existing gesture/fling dispatch for all other sources. No broad gesture allowlist, custom-source API or new gesture system; if a future fitCamera/custom move is introduced it must define source ownership then. Programmatic presentation also cancels pending debounce before moving. User movement updates live camera without changing remembered committed anchor until accepted settle.

Effects capture owner/token and the exact intended mode object (or pre-admission mode for a queued route); on execution check mounted and reference ownership before widget/context/controller access. The failure observer checks the returned fallback mode after notify before capturing its feedback token. Reentrant listeners before or after the Screen presentation observer, including equal-identity local selection and equal-value Explore, cannot authorize a stale success/feedback. Do not rotate the token on every VM notification. Replace build's _scheduleCallbackOnNextFrame flag by one effect scheduled per accepted operation. Retain extent targets Explore 0.3, Search 1.0, Post 0.5, existing zoom16/offset and local controllers. Remove only dead scrim state/commented renderer. Explicit close clears input and commits actual live camera; system/predictive Back and Gallery stay route-owned.

## Risks / Trade-offs
