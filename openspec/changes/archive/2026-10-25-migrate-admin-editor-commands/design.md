## Goals / Non-Goals

**Goals:** Make accepted intent, field snapshot, publication authority and physical settlement distinct and testable; preserve route and backend contracts; remove exactly all 37 B0 diagnostics without new diagnostics.

**Non-Goals:** No adopted create ID, save-in-place workflow, draft persistence, new navigation, queued writes, automatic search/preview retries, new packages, generic scheduler, backend changes, foundation changes, canonical sync or legacy-file deletion. `improve-admin-submission-editor-workflow` is stale and unapproved; do not adopt its capability, artifacts or behavior. The ordinary-continuation exception is already approved by migration-1's unsynchronized delta for `Only authoritative completion can commit asynchronous data`; this change adds uniquely named editor requirements without another competing MODIFIED block. Canonical's older blanket retrieval wording does not silently override that approved migration decision. Existing provenance and publication requirements remain authoritative and are extended only with editor execution safeguards.

## Decisions

### D1 — Admission and mutual exclusion

Create exactly eleven **private ordinary** `ResultCommand<void,T>` instances with existing no-param factories, one persistent reusable instance per lane for the lifetime of the ViewModel. Successful or failed execution settlement never disposes that instance while its owner remains live. Each accepted intent receives a new receipt with a monotonically increasing owner-local execution ID, immutable input, captured input/draft revisions, publication authority and private settlement bookkeeping; the receipt owns one attempt, not the Command lifetime. Capture each accepted request in its file-private typed receipt/slot; even former parameterized commands need not expose text/group content in command paramData. Public API: synchronous `bool requestLoad()`, `requestSave()`, `requestReject()`, `requestPromote(AdminPromotionTarget)`, `requestLink(int)`, `requestPreview()`, `requestFindCandidates()`, `requestApply()`, `requestKeepCurrent(AdminEventMergeGroup)`, `requestAddAsset()`, `requestDeleteAsset(int)`. True means admission only; durable success is exclusively the operation snapshot. No public Command, run, execute or runAsync; no public Future falsely completing a rejected operation as successful.

First check live owner, own lane, pairwise gates; reserve the lane and any mutation ownership, capture request, invalidate relevant read authority and set a cached loading snapshot **before** any notify or command run. A refused request creates no receipt, consumes no execution ID, changes neither desired input nor any execution snapshot/accepted slot, produces no terminal result and queues no work. Input changes are a separate setter operation (D4). Do not overwrite an admitted slot on rejection. After any synchronous notification, recheck live receipt identity before action dispatch. A reentrant owner dispose before run marks that receipt skipped without I/O; only because the owner is revoked does D7 subsequently permit deferred physical Command release. The deferred action checks owner/receipt again before every not-yet-started phase. Reserve through the safe terminal barrier (D7), not merely until repository await finishes or upstream first idle notification.

Same-command and busy cross-command refusal returns false, performs no I/O/queue/join, preserves current snapshots and does not generate an independent success. **Intentional narrow difference:** legacy same-command refusal was silent but cross-command busy guards produced an attempted command Result.error. Cross-command busy now uses the same explicit admission refusal as migrations 5–6, so it cannot overwrite an active execution or trigger stale feedback. UI callbacks return on false; enabled/disabled state uses the identical VM gates. Normal eligibility/validation errors for an otherwise admitted attempt still produce original expected Result.error and existing UI feedback; dirty-load refusal is explicit below. This is not a claim of identical legacy busy terminal behavior. Tests distinguish refused admission from admitted failure and retry.

For simultaneous Pv+Fc, apply BOTH rows; Kc is refused because Pv is active. Mutation ownership is one of eight lanes Sv/Rj/Pr/Ln/Ap/Kc/Aa/Da; no two are admitted together. Fc is advisory, does not exclude mutations, and mutation admission invalidates old candidates. A search admitted during a mutation is invalidated by any later relevant state/source/hydration commit, never grants moderation readiness. Pv→mutation asymmetry preserves the existing allowance (except Kc) with explicit invalidation; mutation→Pv remains refused. Ld is intentionally exclusive with all eleven operations, including reads: hydration replaces the entire editor/assets and cannot safely overlap accepted work. This strengthens legacy's unguarded Load, justified by its destructive hydration, not speculative scheduling. Public Load also refuses a loaded dirty draft without clearing it; initial/retry load remains available. Internal resolution refresh uses the same hydration helper with the outer receipt's private authority, not public Load admission.

The matrix governs request admission only. `setCandidateSearch` is not a request column: while live it may change desired input and invalidate candidate publication during any row (including Load or another mutation), without changing reservations or starting I/O. It is a no-op after owner revocation. Every N/S cell for requestFindCandidates() is observationally inert; any preceding setter invalidation is separately attributable and must be asserted before calling request. No automatic work is queued. Continuous busy input may require an explicit retry; no already accepted operation is lost, duplicated or reassigned. A refused newer preview/search is not an accepted latest intent. One local receipt representation and narrowly scoped settlement helpers may cover eleven concrete lanes (Rule of Three); do not extract new shared framework code.

### D2 — Save and KeepCurrent

Save captures immutable persisted fields at admission, including independent nested JSON Delta maps/lists, category normalization, coordinates and exact temporal draft, plus submission ID and monotonically increasing draft revision. Validate required city/name, date policy and paired finite/ranged coordinates with existing rules before I/O, reporting expected errors through the command. Capture validation outcome/request without rereading mutable fields at deferred entry. Create stays create iff the route's immutable ID is null; do not adopt returned identity. Update uses precisely the route ID. Contributor display data remains absent from the input.

After a successful Save: while owner/receipt live, invalidate preview; clear dirty only if current draft revision equals the persisted snapshot's revision. Do not hydrate response fields or erase later changes. If programmatic/stale field callbacks change a draft while Save is pending (UI already locks ordinary editing), keep the newer draft dirty. Success means the captured snapshot was persisted, not that newer values were saved. Screen may pop only for the matching success AND clean matching revision (`canCloseAfterSave`, derived from the matching terminal snapshot's retained persisted revision and current draft revision, not a second success flag). Retain only that small terminal revision association after private receipt retirement; clear it at the next Save admission. A clean matching Save must still authorize closure when a status dialog returns after physical receipt cleanup. No pop on a later-dirty draft; existing Save remains available for explicit retry. No follow-up auto-save. This closes the observed unconditional dirty reset without adopting the stale workflow.

KeepCurrent admission captures the **current preview identity/revision, target and complete group.current**, rejecting an old group not belonging to the current preview with an admitted expected failure. It copies all fields of exactly one of name/category/description/location/schedule, updates hydration once and draft revision once. Its outer mutation receipt owns the entire chain: copy→private save→private preview. Neither helper calls a public façade or attempts a second mutation reservation. Replace `fromKeepCurrent` booleans with the captured private receipt authority; no public bypass/force flag. No independent Save snapshot/success notification is emitted, so inner Save cannot pop the screen. Save expected failure leaves copied dirty values, stops preview and returns same error. Save raw throw belongs to outer KeepCurrent runtime once. If an internal/reentrant authorized field revision differs while internal Save awaited, preserve dirty, stop preview and return expected draft-changed failure; already committed Save is not described as rolled back. If target/preview context changed, do not publish old-context success or preview; require new explicit preview. On normal same-revision Save success, internal Preview captures the **post-save** generation and uses the same outer authorization despite Kc being busy. Its result determines KeepCurrent outcome. Dispose between phases starts no next I/O and publishes no synthetic success.

Alternative rejected: public Save/Preview command recursion (self-rejection and extra UI completion), clearing dirty on any success, allowing a create response to change route identity, or a new generalized workflow engine.

### D3 — Moderation and backend integrity

Before mutation I/O retain persisted ID, successful detail load, clean/Pending state, own receipt and exclusive mutation ownership. Promote requires concrete category and Event temporal validation; Link requires non-null start and exact requested ID; Apply requires imported update and preview matching current target/revision/source context. Snapshot ack flag, acknowledged hash and ignore option at admission. Target changes during a mutation are refused synchronously; captured intent cannot be reinterpreted before deferred entry. Source-checkbox changes after admission cannot alter captured payload. Public persisted-field setters refuse edits while public Load is reserved or Reject/Promote/Link/Apply/KeepCurrent/AddAsset/DeleteAsset owns the mutation reservation; internal KeepCurrent copy is authorized by its own receipt. This mirrors the disabled form and prevents accepting new edits that successful moderation would make read-only and pop. Save permits a newer draft defensively and uses D2 revision protection; Load hydration also checks revision. Target changes during any mutation are refused. Rejected stale setter callbacks do not change fields, dirty or hydration revision; expose their refusal to direct callers where a return value is needed, without a new state channel. Synchronous owner-disposed setters always do nothing.

Backend remains authoritative: Reject discards one source revision, optionally ignores future revisions; Promote creates explicit target/linkage; Link accepts against existing active Event without content/media copy; Apply sends original preview Event/submission token strings with no DateTime round-trip, sorting or token replacement and no client-authoritative merge group calculation. Preserve same-target already_promoted/already_resolved payloads and conflicting-target errors. Reject maps its repository resolution to void only AFTER retaining pendingId for follow-up. No direct table writes, new RPCs or client transaction emulation.

`_refreshAfterResolution` retains ordering inside the same outer ordinary action: for external mutation Success or typed `SOURCE_CHANGED`, clear ack/hash/preview and increment preview generation synchronously; notify only live; check authority again, then refresh **original submission ID**, then if live and original mutation resolution has pendingId, fetch that follow-up ID. Other expected errors skip refresh. Reject's original resolution is retained until this process ends. No outer-ID replacement/navigation to follow-up. Expected detail-load error retains existing fields and remains a refresh failure; it does not replace the original mutation outcome or skip the follow-up if one exists. Expected follow-up failure retains existing follow-up data and never invents an ID or success object. Final status/promotion/target commits follow the original mutation result as before. Clear stale preview/source acknowledgement even when refresh fails.

Hydration authority additionally checks the draft revision captured for that refresh: a newer local edit is retained rather than overwritten; invalidation/ack revocation still occurs. This applies to public Load too. On SOURCE_CHANGED the original expected failure remains visible after refresh, with renewed explicit acknowledgement required. On disposed owner, after any await or notify, no hydration/follow-up/final state commit or new call starts. An already started remote resolution may have committed.

Preserve the current raw-refresh failure boundary: these are private direct helpers, not nested Commands. A raw detail/follow-up throw aborts the outer action, reports original Object/stack once through that outer command and yields its runtime failure. No child Command reports it a second time, no catch-and-success, and no automatic remote mutation retry. A raw read failure after a remote commit cannot prove rollback; this ambiguity is documented. Expected read failures remain Results and do not turn successful resolution into failure. Creating independent child refresh Commands would add error/ownership machinery without a required consumer.

### D4 — Candidates, target and preview

All three reads are ordinary single-flight because user search, preview and load are explicit actions and the existing UI disables repeat execution. There is no typeahead or requirement to accept B while A is pending. RestartableCommand is available but not justified here; if a later requirement makes candidate search reactive, it needs a separate reviewed policy. Do not silently turn a refused request into queued/latest-wins work.

The VM owns the desired raw input and candidate-input revision. Its sole input API is `void setCandidateSearch(String value)`: if live and the value differs, store the raw text, increment the monotonic input revision, revoke publication authority of the admitted old candidate receipt, clear obsolete candidates/inline candidate feedback and publish a neutral candidate snapshot before notifying. Equal raw text is a no-op; A→B→A still increments twice and cannot restore the first A. The setter can run while any operation is physically pending, including another mutation or Load, but never changes that operation's input/reservation and never runs or queues a search. Disposal makes it a no-op. Candidate invalidation does not invalidate an unrelated mutation or its terminal outcome.

The sole search execution API is `bool requestFindCandidates()`, with **no parameter**. Check live owner, lane availability and the D1 matrix before any change to execution state. On false: no receipt or execution ID allocation, desired-input write, slot overwrite, snapshot/feedback change, I/O, queue or terminal outcome. On true: capture the VM's current raw input, its input/context revisions and the existing normalized transport value (`trim()`; empty becomes `searchName: null`) in a new immutable receipt; reserve and publish that receipt's running state before notification/run as D1 requires. The private Command remains no-param, so query text is not in command paramData/log wrappers. No request calls the setter. UI onChanged calls the setter; Search button calls only requestFindCandidates(). Tests/helpers use these same two entry points.

Draft changes, hydration, source/hash changes and resolution/mutation commits revoke advisory result authority separately from desired-input editing. Target changes invalidate preview and candidates conservatively, even though candidate transport remains target-independent and adds no new targetEventId argument. A candidate request accepted during a mutation captures that moment's context and can be invalidated by a later relevant mutation commit; changing input during that mutation never causes implicit search. A stale candidate success or expected error publishes neither data nor feedback; stale raw failures still report the original Object/stack once through the retained Command, without stale UI feedback. User explicitly searches the current desired input after physical settlement. Candidates remain advisory and never enable Apply or satisfy clean/Pending requirements.

Preview request captures ID, target, preview generation and source context. Every target selection increments generation even A→A; A→B→A cannot restore an old A preview. Dirty transitions, Save admission/commit, hydration, source revision changes and moderation/asset mutation admission invalidate preview. Suppress BOTH stale preview data commit and its public terminal snapshot; do not show a completed incompatible preview as current success or retain an old inline error. On invalidation cached read snapshot becomes neutral while its private physical reservation remains busy; after settlement it stays neutral, enabling explicit retry. UI busy derives from owner reservation, not neutral snapshot alone. The same rule applies to invalidated candidates and to a Load whose hydration revision became stale. Raw failures still globally report once even when public outcome was revoked.

For current Preview success, install merge preview and returned current source display; if currentSourceHash differs, revoke previous ack/hash before notifying. This source display update is part of that same authoritative preview commit; do not accidentally invalidate the result being installed by treating it as an unrelated external hash event. It does revoke any older candidate context. Apply availability requires a current committed preview tied to exact generation/target and clean persisted fields, never simply `previewSnapshot.completed`. Expected EVENT_CHANGED/SUBMISSION_CHANGED preserve specific feedback and require fresh preview before another Apply (clear invalid preview on these token errors); SOURCE_CHANGED follows D3. This prevents stale tokens from keeping Apply enabled while retaining server retry/idempotency authority.

### D5 — Assets and irreversible phases

Retain maximum asset count, persisted/loaded/Pending guards and dirty-permitted asset edits. Admission owns the asset lane from picker through association settlement. Captured asset ID and submission ID cannot be replaced by a second request. Add: gallery picker→live check→upload task stored as active→await upload Result→live check→repository association→live check→append only returned confirmed asset. Result.error at upload or association propagates unchanged and retains confirmed list. Picker cancel remains live Success<void> no-op, no feedback/navigation. Delete checks captured membership at admission, calls repository once and removes only confirmed success. No optimistic list deletion or claim of backend exactly-once beyond existing contracts.

| Revocation point | Required private behavior |
|---|---|
| Before deferred entry / picker entry | zero picker/upload/repository calls |
| Picker pending | picker may resolve; do not create upload after revoke |
| Upload pending | call active task.cancel once; retain command until task really settles; do not associate, publish, retry or invent remote rollback |
| After upload / before association | authority check prevents association if revoked; uploaded object may remain remotely |
| Association pending | cancel active task best-effort if still referenced; this cannot cancel a repository/SQL transaction; let it settle privately, do not append/notify |
| Delete pending | remote deletion may commit; no local list publication after revoke |
| After backend commit / before terminal | no rollback claim, no local feedback/navigation, retire safely |

`finally` clears only the identical active task. No second cancel from deferred cleanup. Keep existing task cancellation semantics; no forced completion, timeout, storage cleanup protocol or staged create assets. Association response loss may remain ambiguous and retries may duplicate association; existing constraints do not establish end-to-end exactly-once. Accepted raw picker/upload/repository throws stay runtime failures under the owning Add/Delete command, once only.

### D6 — Result snapshots and UI effects

Expose eleven cached `<operation>Snapshot` getters with existing ResultCommandSnapshot projections: idle, isRunning, completed, domainError, unexpectedError, hasFailure. Keep loading/operationRunning/assetMutationRunning and `canRequest...` derived from reservations to cover the pre-action window. Initial null is neutral; Success<void>(null) is real success; Error<T> retains its original Exception; raw throws remain unexpectedError and global original Object/stack once. ### D7 — Owner lifetime, settlement and cleanup

#### Persistent Command ownership versus one execution

The ViewModel owns eleven reusable Command instances from construction until owner revocation plus safe physical cleanup. No Command is disposed, replaced, recreated or re-subscribed merely because an execution returned Success, Result.error, handled raw failure or an assertion. Each admitted attempt gets a **distinct** receipt/ID; at stable settlement only that receipt and its lane reservation are released. If the owner is live, the same Command and stable listeners remain available for explicit retry with a fresh receipt. Disposing a receipt means releasing its private request/bookkeeping, never Command.dispose(). Preserve only the small authorized terminal ID/revision association needed by D6, separate from the receipt.

#### Stable observer ownership

Install exactly one private results observer and one private isRunningSync observer per lane during VM construction, before public forwarding; retain them across every live execution. Each callback resolves the lane's current receipt and returns if absent/settled. A running transition advances only private settlement state and does not reinterpret an old retained terminal snapshot as a new result. A results callback captures only a real result belonging to that receipt's started physical run; blank/retained prior results do not count. Public forwarding is a separate stable subscription, installed once, checking live owner/current receipt/publication authority and attaching the D6 execution ID before notifying. Action continuations and queued barriers capture their exact receipt rather than looking up a newer one after await. No execution installs a second result/running/forwarding listener, and ordinary live settlement removes none of these lane listeners.

Because the lane is serialized through the safe post-dispatch barrier, a fresh run begins only after previous upstream dispatch/finally work is drained. A private callback without an active receipt is ignored. A callback/barrier explicitly tied to an old receipt must check its identity and settled flag before touching the lane; it cannot publish to a newer receipt or clear its reservation. Private settlement observers remain after public forwarding is detached on revoke; they perform private bookkeeping/error-safe cleanup only and can never restore public authority.

#### Settlement barrier and reusable-lane state machine

Reuse the already implemented `AdminSubmissionsViewModel._observe/_actionSettled/_scheduleSettlement/_settle` at `lib/ui/admin/submissions/view_models/admin_submissions_view_model.dart:344-460`, scoped locally to editor receipts, without its refresh drain/orchestration. Each private results/running transition and action-finally witness increments the current receipt's settlement revision (distinct from its input/draft revisions). At most one queued barrier captures receipt identity and settlement revision, crosses **microtask → event**, then checks: not settled, same receipt still owns the lane, physical synchronous running false, action-finally witnessed or dispatch explicitly skipped, and captured revision still current. A changed revision schedules one fresh barrier; still-running work waits for its next actual transition, never polling. Neither first idle, terminal observation nor action-finally alone reopens admission. The upstream reporting/finally path must finish before safe release.

Mark the receipt settled once, clear the lane only if it still references that receipt, and release its immutable request/bookkeeping. While the VM is live, keep the physical Command, both private observers and forwarding subscription installed; notify safe reopening after the barrier. Do not clear an authorized terminal ID/revision association just because its receipt settled. Reentrant admission from terminal notification is refused; explicit admission after reopening creates a fresh receipt and stays busy despite any old callback. Normal terminal, assertion-abort and skipped dispatch remain distinct: assertions retain fail-loud policy without a fabricated business outcome.

| Transition | Receipt/reservation | Physical Command and listeners |
|---|---|---|
| Construction → live idle | No receipt, neutral snapshots | Eleven instances/listener sets installed once |
| Live idle → reserved | Fresh monotonic ID, immutable input, loading; prior terminal authority superseded | Reuse same instance/listeners |
| Reserved → deferred/entered | Same receipt owns all phases | Retain instance; check authority before each new phase |
| Entered → action-finally/terminal | Witness/terminal observation only; reservation still held | No disposal or observer detach |
| Stable barrier → live idle | Settle original receipt once; release only its reservation/request | **No Command disposal/detach**; ready for next explicit attempt |
| Reserved → skipped due to reentrant revoke before run | No I/O/public terminal; settle skipped receipt at safe barrier | Owner revoked: release idle instance once, outside dispatch |
| Any live state → owner revoked | Refuse new intent, freeze public snapshots, remove public forwarding | Idle lanes release deferred; active lanes retain private observers/Command |
| Revoked active → stable physical settlement | Private receipt settles once; no new phase/public commit | Remove stable private observers then Command.dispose once outside dispatch |

#### Owner revocation and final physical cleanup

Dispose is idempotent: synchronously mark owner revoked, reject setters/requests, invalidate publication/phase authority, detach every public forwarding subscription once, cancel active upload once and freeze cached public snapshots. Defer super.dispose outside a current VM notify stack. Already-entered callbacks may finish their stack; recheck authority after every notify/await before any new phase. Clear transient request payload when safe; keep the exact receipt and necessary private physical witnesses while its operation remains pending.

For a lane idle at revoke (never run or already safely settled), schedule revision/identity-checked microtask→event cleanup outside dispatch, remove its stable private results/running observers and dispose that physical Command exactly once. For a reserved/deferred/entered lane, **do not** dispose the Command or remove its private observers until that receipt safely settles, including normal/expected/raw/assertion outcomes and skipped entry. At its post-revoke stable barrier, release the receipt, remove the private observer pair and call Command.dispose once. An owner-live settled lane can be reused indefinitely; only revocation makes its physical release eligible. A per-instance released guard makes competing idle/active cleanup callbacks idempotent. No old receipt cleanup may target a newer active receipt.

Late raw error beyond upstream's 50ms notifier teardown still reports the original Object/stack once because the active Command was retained. Assertions can bypass normal result routing; the finally/private barrier cleans settled work without synthetic terminal results or continuation. Nonterminating physical work retains its Command/private observers honestly; no timeout, forced completion, polling or cancellation fiction.

Direct internal helpers remain phases of the same outer receipt: KeepCurrent owns copy/save/preview; moderation owns mutation/detail/follow-up. They do not create receipts or public Save/Preview/Load completions and do not detach reusable lane observers. Phase transitions require the same live receipt after every await AND notify. No foundation, global scheduler, reporting or RestartableCommand changes are required. Test-support lifecycle observation may expose read-only IDs/counts if needed to discriminate physical disposal from receipt release; it must not expose Command handles as consumer APIs or replace factories globally.

## Risks / Trade-offs

- Busy cross-command refusal is now explicit synchronous admission=false instead of an attempted failure snapshot → document and regression-test this intentional change; preserve real validation/error/retry results.
- Load becomes exclusive and dirty-protected → prevents destructive hydration without adding a queue or autosave. Initial route/retry and internal authoritative resolution refresh remain supported.
- Single-flight candidate/preview invalidation may require another click after settlement → preserves explicit search UX and refused-intent semantics; no hidden deferred request.
- Persisted snapshot success with newer edits cannot close the route → preserve draft and require explicit Save, without create ID adoption. Create response-loss/second create ambiguity remains existing behavior.
- Remote mutation/association/delete cannot be undone by local dispose → no cancellation/rollback claim; backend idempotency/constraints remain authority.
- A raw refresh error can follow remote commit → retain original runtime diagnosis; never replay mutation automatically or fabricate rollback/success.
- Physical Future may never settle → private resource retention is the honest limit; no timeout/polling infrastructure.
- Local SDK/CI native ObjectBox setup may differ → record environment preparation separately, use existing CI instructions, never mislabel skipped service integrations as passed.
