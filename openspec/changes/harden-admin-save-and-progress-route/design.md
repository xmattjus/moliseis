## Goals / Non-Goals

Activate one coherent durable editor and remotely reliable Save without a second session manager. Keep local arbitration independent from HTTP and widgets. Distinguish confirmed work, physically durable work and unknown outcomes.

No owner retirement is needed. No generic operation journal, recovery inbox/ack protocol, native fork, new state package, automatic uploads from recovery or automatic remote retry at startup. Plan 3 adds richer conflict recovery and Plan 4 adds dirty-exit choices. This plan still supplies settled failures, return-to-editor, explicit reload/retry policy and preserved work for every activated path.

## Decisions

### 1. One application owner, existing session and Commands

Register Admin draft/staging repositories and one Admin editor VM in `dependencies.dart`. Wire auth through the existing Provider/auth lifecycle so account or staff-authority loss synchronously revokes publication and local session authority before any async refresh/navigation. Auth listeners detach on application disposal. Do not recreate a second VM per route or per progress page. The VM composes `AdminDraftSession` as its sole local state boundary; editable fields project C instead of keeping a second mutable authoritative draft.

Activation is an explicit idempotent VM request for account + new/existing target, initiated by a small route-binding lifecycle, not repeatedly by build. A same-target rebuild shares initialization. On a real replacement, capture a new generation even for A1 → B → A2. Reuse the foundation's refusal of uncheckpointed work or unsettled local mutation; also refuse normal target replacement during admitted remote mutation. Refusal displays a settled return-to-current-editor state, without changing the active draft, autosaving or introducing Dirty Exit. The editor has an explicit local-checkpoint action so incomplete fields can be parked durably before a normal switch. Back may leave the route while the app owner retains C; reopening the same target returns to it. Durable checkpoints, not arbitrary uncheckpointed process memory, survive process death.

Every rendered setter, dialog, picker continuation, load, moderation action and terminal effect captures account/session/target/activation authority when established. A callback must not acquire new authority when it finally runs. Existing candidate/preview/editor revisions remain additional guards, not replacements for activation. Rebind field controllers only on accepted hydration/restoration, never on every notify. Clear transient contributor/moderation/source/preview/search context on activation/revocation; contributor identity is not local account ownership.

Commands remain `createResultCommand` single-flight with synchronous reservation and physical-settlement barriers. A revoked operation loses publication and authorization to start later remote phases immediately; already-sent HTTP may commit. Do not dispose a physically running Command, drop its settlement witness, reuse its snapshots for a new activation, or convert raw programming failures into Result.error. Retain a global physical mutation reservation until its current action settles, even if account B activates after revocation; B can restore/edit locally but cannot start a conflicting remote mutation until the old reservation releases. This avoids allocating Commands per session or trusting `isRunning` alone. Stale success/error releases only its own reservation and cannot publish into B/A2. Application disposal follows existing deferred command release.

### 2. Durable activation and hydration

Retain all Plan 1 immutable fields, raw coordinates, incomplete event dates, deep-frozen Delta, size/count rules and absent/valid/unknown outcomes. C is current, E effective local comparison, P last actual checkpoint, R confirmed remote observation. Local dirtiness C≠E is separate from remotely unconfirmed fields and staged work. Restored R is historical, insufficient for current moderation/capacity authorization.

Use admitted hydration tokens for remote getById; publish only through the local boundary after latest-request and local-intent checks. A protected field snapshot may coexist with separately observed pending/status/assets, but incompatible editable remote context must mark Save/moderation unavailable rather than silently overwriting or pretending it is compatible. Preserve local work and expose a settled conflict/unavailable message plus return/reload; no merge/discard UX is added. Load failures terminate loading and support explicit reload. A compatible metadata refresh retains checkpointed unconfirmed edits. Neither a saved P nor old R establishes fresh staff/status authority.

A local checkpoint captures fields inside arbitration and can finish A after typing B: P/E become A, C stays B. For remote Save, extend this boundary with a narrow captured-attempt checkpoint operation: Save synchronously captures immutable A + revision, then writes that exact A without recapturing later B. A later explicit checkpoint B must remain newer. Confirmation updates R for A without replacing current B or overwriting a physically newer checkpoint with A. Persist updated remote-baseline metadata on the latest P snapshot, preserving its fields and E meaning. Local-write failure leaves disk truth unchanged and reports partial/local-repair work.

### 3. Create contract and crash-safe target adoption

Reuse local session UUID as `client_submission_id`. Extend Admin Create validation/repository/store types; require UUID-v4 for the new client request. Edge still authenticates/authorizes every replay and derives creator account/profile; no client user_id authority. Use a small service-role-only SECURITY INVOKER Admin Create RPC, with explicit search_path and revokes from PUBLIC/anon/authenticated. Insert with `ON CONFLICT (user_id, client_submission_id) DO NOTHING`, then in a subsequent READ COMMITTED statement fetch the existing ID when not inserted. This waits for same-key contenders and avoids read-before-insert races and the same-statement snapshot trap. Never use `DO UPDATE`, including a no-op update which could fire timestamps/triggers. Return created/replayed plus authoritative getById detail/assets; replay first-write-wins even with changed input or moderated data. Do not copy Public quota rows, rate limiting or inline-asset submission transaction. Public replay semantics remain unchanged.

Before a field write, persist one narrow unresolved field-write intent within the versioned draft payload: Create or Update, captured valid input/snapshot A, target, exact expected remote field-version token for Update, stable session UUID and attempt identity. Create uses the UUID as its server replay key; Update records unresolved outcome without claiming server idempotency. This intent is necessary to replay the original valid request after response loss even if a later local checkpoint B is incomplete. It is not a general ledger or a promise of an uncommitted remote row. Preserve it across field checkpoints. Atomic confirmed adoption clears Create intent; a confirmed Update clears Update intent only in the durable local baseline settlement. This is one outstanding Save safety record, not a history or general-purpose ledger. On reopen with Create intent, editor restoration is immediate; only an explicit Save/retry replays that intent to discover/create the authoritative record. Do not issue another key or auto-submit during initialization. Restored Update intent instead enters terminal unknown/read-back mode before normal Save admission: compare against its captured A, not newer P=B. Never infer that the HTTP was unsent from an old read-back, a restart, timeout or absent response; an old server request may still be running. Nonmatching/incompatible read-back remains blocked for remote mutation, with local editing/checkpoint and return available. Matching read-back confirms the observed projection; safe subsequent writes additionally require the conditional server predicate described below, not an inference that the old HTTP finished. Even interruption between intent commit and HTTP send enters explicit read-back recovery; do not add an unguarded resend shortcut.

Adoption is a domain-facing repository operation implemented as ONE ObjectBox write transaction over existing draft and staged rows. Verify exact old account/session/new owner, current technical row, and destination account/ID occupancy; change lookupKey/submissionId on the same draft row and submissionId on every same-session descriptor, preserving technical IDs, stable local UUID, order, paths, bytes, latest checkpoint fields and receipts. Update recorded R and clear pending intent atomically. No file move/copy is required because paths exclude target. Existing-target adoption of an equal already-adopted owner is idempotent. Conflicting destination owner or malformed rows returns unavailable without merging, duplicating or deleting either owner. Preserve the confirmed response in RAM for local-only adoption retry; after death, retained old intent replays the same UUID. An already-occupied destination is a terminal local conflict requiring later recovery, not permission to erase work.

Crash cuts: before Create → durable intent retries; remote commit/response lost → same-key replay; response/adoption not committed → old row/descriptors and intent survive; during adoption → ObjectBox transaction leaves all-old or all-new; after adoption → remote lookup and Update, never Create. A restored `/new` URI with the exact resume session resolves its adopted target by account/session lookup rather than allocating another new draft. Add a narrow load-by-session lookup to the existing repository for this case; do not add duplicate alias owner rows. Fresh explicit New without a resume session still activates the new slot.

Adoption invalidates old target-bound setter/capacity/hydration tokens and rebinds the editor to fresh authority under the same logical session. The admitted Save continuation is allowed exactly this confirmed old→new transition through its captured lease; it cannot authorize arbitrary replacement. No other stale callback receives the new authority. If a replay reveals different or moderated fields, adopt identity/status but preserve C/P, stop staged persistence and report conflict/read-only. Do not silently Update replayed content in the same attempt. A later explicit compatible pending Save can Update; replay itself never overwrites moderation.

#### Necessary Update fencing dependency

Independent review demonstrated a race beyond Create replay: an old Update A may still execute after process restart and overwrite later B, even if a read-back happened to show A. Add a conditional Update predicate using the existing DB-owned field `modified_at` token, alongside id and pending status, rather than introducing a revision column, operation ledger or general conflict workflow. The provenance trigger already advances this value monotonically for real editable projection changes and preserves it for no-op field updates. An old request with expected token V cannot change a row after a later field Save advances it beyond V. Keep existing imported-event/provenance/status guards.

Carry the exact raw server token string through wire/domain baseline and durable Update intent without JavaScript Date or lossy timestamp round-tripping. The display DateTime is not the token. Old stored baselines lacking the token need fresh detail before conditional Save. Validate the token shape at Edge; use the guarded UPDATE itself as the concurrency boundary, never a read-then-unconditional-write. Return typed `SUBMISSION_CHANGED` when token mismatch blocks a pending existing row. Do not overwrite the remote row or discard local fields on that outcome. Skip field Update entirely when captured input already equals a freshly confirmed projection and only staged work needs persistence.

Read-back of A with a changed token makes outstanding expected-V work obsolete; read-back of A with unchanged V can still have an outstanding no-op A, but any subsequent changed B is also conditional on V, so whichever changes fields first fences the other. A changed/mismatching read-back remains settled conflict/unknown, never an automatic overwrite. Explicit safe retry of the same unresolved Update uses the same captured fields and expected token, not a fresh borrowed token. This is a bounded prerequisite of crash-safe Save, not Plan 3's conflict-resolution UX. Verify delayed old A versus new B in real PostgreSQL, no-op A, same-token concurrent writes, old-DB precision, moderation/import races and trigger semantics. Public schemas/API are unchanged.

### 4. Small association replay contract

Current `add_submission_assets` serializes by parent row but blindly inserts; schema has no unique asset identity. Adding global URL uniqueness would change legacy/Public semantics, and another per-asset UUID is unnecessary for this bounded contract.

Add an Admin-only service-role singleton RPC for staged receipts. Under the existing parent row lock: find the lowest-ID association whose canonical URL, width, height, MIME and duration exactly match the captured upload receipt (null-safe equality); return it as replayed BEFORE pending/capacity checks. Same URL with conflicting metadata returns a typed conflict, not a new row. If no existing match, require pending and delegate insertion to existing `add_submission_assets` inside the same transaction/lock. Return created/replayed association with validated payload. Missing parent/not-pending/full remain terminal typed outcomes. Existing direct table permissions and grants remain restrictive. All supported association writers/deleters continue using the parent lock.

For this Admin staged contract an identical uploaded receipt on one parent means one association, even when selected twice; it is not byte deduplication inferred from URL. Legacy duplicates are not deleted; deterministic lowest-ID replay does not create another. This narrows Admin staged insertion only; ordinary persisted immediate-add and Public batches keep their current RPC. Delete-versus-replay serializes; after an intentional committed delete, a new explicit pending association can recreate the receipt. No tombstone or exactly-once lifetime claim. Stale automatic replay cannot run after local remove/session revocation because the captured mutation gate/attempt authority is checked. Real PostgreSQL tests, including cross-RPC fifth-slot races, are mandatory.

### 5. Staged Save, receipts and retention

Extend staged persistence with a separate optional versioned receipt payload on the existing staged entity, exposed via a small immutable domain progress value. Local descriptor/path identity stays unchanged; repositories still never upload. Receipt records confirmed `SubmissionAsset` and optional confirmed association ID, bound to account/session/digest/target. Old rows decode as local-only. A malformed receipt blocks remote retry for that item without deleting valid bytes. Do not put upload metadata into the raw relative path or use it as proof of database association.

Save phases, owned by the VM and existing Command:

1. Synchronously validate authority/admission and capture immutable fields, owner/activation/revision, and stable staged descriptor identities/order. Local mutations already in arbitration settle before final membership validation; unknown storage/capacity refuses the attempt. Navigation follows admission, not eventual completion.
2. Checkpoint captured snapshot and unresolved Create/Update intent. Failure starts no HTTP. Keep typing B permissible; prevent removal/replacement of captured staged items while their attempt owns them. Local staging/checkpoints already admitted can commit in local order; uncaptured new items remain pending for the next Save.
3. Create/replay or pending-and-version-guarded Update outside local arbitration. Adopt Create identity before uploads. Update response confirms only its field projection; its empty asset envelope must not clear known associations. When fresh complete assets/status are needed, explicitly getById under captured authority.
4. For each captured unconfirmed descriptor in persisted order, resolve private file, upload only if no confirmed receipt, persist confirmed upload receipt before association. If receipt persistence fails, stop; retain live receipt for local-only write retry. After restart the unavoidable upload-response-before-local-write gap may require existing Cloudinary deterministic duplicate lookup again, not blind new upload identity.
5. Associate the exact receipt through Admin replay RPC, then persist association confirmation before removing that descriptor. If response is ambiguous keep receipt, retry only that replay-safe association. If confirmation-write/removal fails, retain receipt/file/owner; replay or exact confirmed-row reconciliation repairs it without another upload. Descriptor deletion precedes best-effort file cleanup, as Plan 1 requires. Complete authoritative detail refresh avoids double-counting associated-and-staged receipts for capacity.
6. Confirm R for the saved fields, preserve newer C/P and uncaptured staged work. Completed means all captured work is confirmed and required local metadata commits settled; new B/new staged work remains visibly unsaved. Partial success never returns to Create after identity is known. Moderation remains blocked while any staged/ambiguous/local-repair work or remotely unconfirmed fields remain.

The durable field-write intent is independent of the runtime Command and must survive until its outcome/baseline is durably settled. States are local-only bytes; confirmed uploaded receipt; confirmed association; unknown response at the current remote boundary. Running stage and terminal outcome are a small VM value keyed by attempt identity, projected alongside Command state, not a second execution system. Unknown is never success. Expected recoverable boundary failures remain Result.error with phase/outcome details. Unexpected exceptions use existing global reporting and settle to an unexpected terminal screen with no automatic retry.

| Terminal condition | Allowed continuation |
| --- | --- |
| Validation/checkpoint failure, no remote request | Return to editor; fix/retry explicitly. |
| Create transport ambiguity | Retry captured Create intent with same UUID, then adopt; never new key. |
| Create confirmed, local adoption failed | Local-only adoption retry with live response; after restart same-key replay resolves identity. |
| Update response ambiguous | Retain durable unresolved Update intent across restart. Do not automatically resend Update: explicit read-back compares current pending projection with captured A. Equal confirms the observed A with conditional server fencing for future writes; different/missing/moderated remains settled unknown/conflict with local work preserved and mutation blocked. Return/reload is always possible; richer resolution is Plan 3. |
| Partial upload success | Retry skips confirmed uploads; unstarted files remain. Ambiguous upload uses existing deterministic Cloudinary path and is not DB-confirmed. |
| Association response ambiguous | Retry captured exact receipt through replay RPC; no upload repeated. |
| Not pending / missing / capacity / receipt conflict | Stop later phases, retain unconfirmed files, reload status/assets; local removal remains possible when safe. No blind retry button. |
| Remote success, local receipt/baseline/descriptor commit failed | Local-only repair when evidence survives; after restart read/replay only the unresolved replay-safe boundary. Never repeat confirmed Update just to clean up. |
| Revoked/replaced owner | No later phase or publication; physical reservation settles. Captured committed local work remains original-account private. |

Retain draft owners even when Save completes and the final staged item is removed. No deletion/finalization API, garbage collector, obligation registry or recovery lease is introduced. This directly resolves Update A versus checkpoint/stage B: settle only captured A/items, never clear all session work. Before/after adoption, local tail orders pending acquisition; old-target work rechecks and safely refuses if overtaken, already-committed rows are atomically rebound. Failed file cleanup leaves non-restorable contained residue, with owner retained. Revocation can allow an already-started exact-owner local commit to finish without publishing it. HTTP never holds filesystem/ObjectBox arbitration.

### 6. Progress route and editor/dashboard behavior

Each editor route records its exact local session UUID in restorable route state/query metadata when activation finishes, including `/new`; this metadata is a lookup hint, never account authorization. A cold route binding resolves that session under the current authorized account before presenting editor/progress, without starting Save. A reconstructed progress binding may restore local state, but it cannot admit an operation. Missing/foreign session hints show settled unavailable/return behavior instead of activating a fresh new slot.

Add named `adminSubmissionSaveProgress` at sibling `/admin/submissions/save-progress` (registered before `:id`, so parsing is unambiguous), with session/attempt query tokens for presentation correlation. It obtains the application VM; builders/init/rebuild/restoration never request Save. Keep existing `/admin/submissions/new` and `/admin/submissions/:id`. The editor synchronously calls requestSave; only a true admission pushes Progress. If navigation fails, the already-admitted action remains visible from the editor; do not submit again.

Progress observes running, completed, partial, recoverable failure, unknown, unexpected, and restored-idle/interrupted. While physically running, block AppBar/system/predictive Back and ordinary route exit; auth revocation remains higher priority. On every terminal outcome allow return to the same editor and retain its work. Retry is enabled only by VM phase policy and matching account/session/attempt/presentation; it admits one command synchronously, no widget orchestration. Unknown Update offers read-back, not resend. Reconstructed progress without matching live attempt shows interrupted and return; it cannot claim success or replay a command from URI tokens. Process restoration uses durable draft and explicit Save, not persisted Command state.

Returning uses pop when the original editor route remains. When restored/deep-linked without it, navigate to the exact account-checked resume session/editor. After Create, the old `/new` presentation may remain until return: the same app VM/session is authoritative, and durable resume-by-session resolves the adopted ID. Do not replace the editor with a fresh VM, make a second Create or force getById merely for title changes. Successful Save never pops the editor. Publish/Reject become available according to existing guards only when fields/assets are confirmed; Link/Apply/Keep-current retain their existing operations/routes.

Remove `canCloseAfterSave`, saved-close IDs and `_saveCompletedWhileStatusDialogOpen` only together with the new observer-only Save effects. Preserve dialog session/revision/route authority. A Save admitted while a moderation confirmation is open invalidates its old confirmation via editorRevision; completion must neither close the editor nor execute moderation. Keep-current's internal field save uses the shared durable Update helper without starting/navigating Progress or recursively acquiring the already-held command reservation. It still validates captured preview/source context and refreshes preview as before.

Dashboard `_openEditor` refreshes after either create/edit route returns regardless of bool result, after mounted/owner/account checks. This accepted harmless reload also handles untouched exits; no mutation bus or refresh counter. Dashboard reconstruction already does initial load. Ensure progress return to editor does not masquerade as editor exit.

### 7. Android best effort and independent navigation restoration

Introduce one small application-scoped picker gateway owning the sole `retrieveLostData` entry and normal Public/Admin launch calls. It is platform plumbing, not draft state management or a Command architecture. Start Android retrieval once per process independent of routes/auth. Remove Public screen-triggered/native retrieval from the VM; Public normal staging/submit/finalization remain feature-owned. Non-Android never retrieves lost data.

#### F1 decision — Option B intentionally removes Public lost-media recovery

Select **Option B — conservative universal discard**, under the user's explicit authorization to choose this trade-off in the F1 remediation request. The earlier best-effort permission alone did not establish that the previous Public capability was preserved. Current Public production does attempt recovery: `ContentSubmissionScreen._scheduleRecovery` triggers the VM; `_retrieveLostAssets` retrieves early, waits for its captured restored identity and stages eligible files through `_processAssetCandidate`. Existing VM tests such as `recovers a single lost file` and `acquires lost media early and stages it after draft restoration` assert successful recovery. Plan 2 intentionally removes that behavior: even a candidate previously accepted for a single restored Public draft is now discarded. Ordinary live selection and already-committed staged-file restoration remain supported. Do not call this feature-preserving or describe those successful-recovery tests as merely obsolete internals.

The inspected pinned sources are `ImagePickerDelegate.java` (`retrieveLostImage`, `setPendingOptionsAndResult`, `finishWithSuccess`, `finishWithListSuccess`), `ImagePickerCache.java` (`saveResult`, `getCacheMap`, `clear`) and `ImagePickerPlugin.java` (`ActivityState.release`, Activity detach/reattach). The cache exposes paths/type/options/error, no app request nonce, feature, account or session. Retrieval clears a returned cache before Dart can stage it; a new launch also clears cache. Empty retrieval describes only cache contents at that moment; single-image cancellation without a live callback may leave no result marker. Activity recreation replaces the delegate and need not complete its old callback. None of those events identifies a media producer or proves an older native request has settled.

| Candidate attribution evidence | Decision |
| --- | --- |
| Persisted Dart launch/navigation record matches restored draft | Insufficient: record commit and native launch are not atomic, and native media does not echo its nonce. |
| Only one local draft, visible route or latest feature | Insufficient: an older result can belong to another feature/account/session; current absence of another draft is not native provenance. |
| Empty retrieval, process restart, cancellation or elapsed time | No ownership/settlement proof; delayed old media can arrive after the observation and after a newer record. A live cancellation settles only its captured request. |
| Paths, image type, digest or dedup match | Identify bytes/options, not which native request produced them; neither Public's multiple-media call nor Admin's single-image call supplies a per-session native identity. |
| Original live callback with still-valid captured authority | Continue ordinary selection, not lost-data recovery. Preserve this callback across ordinary resume; do not transfer it to another activation. |

There is no positively established safe **lost-data** subset in this API, even in a retained process or single-draft case. A Dart ticket plus extra inbox/ack machinery cannot manufacture the missing native correlation; a native token/settlement extension would add maintenance disproportionate to the accepted individual-image loss. Do not introduce either here. All `retrieveLostData` candidates are discarded, including apparently eligible Public media, without touching committed staged files. Retrieval can finish empty, throw or never complete without blocking draft load, activation, checkpoint, navigation or explicit future picker requests. No warning is added.

#### F2 decision — normal resume preserves a live request

The gateway wraps each native picker Future with a locally settleable request and runtime-only launch single-flight. Each request captures its feature/account/session/activation and unique launch nonce. A normal success, cancellation or error settles that request through its existing feature path. **`AppLifecycleState.resumed`, inactive/paused/background events and elapsed time alone never abandon it or revoke its authority.** A valid image returned after resume is accepted; cancellation/error after resume settle normally. The inspected `ImagePickerDelegate.onActivityResult` dispatches handling to an executor before finishing the callback, so observing resume first cannot certify request loss. No lifecycle observer guesses Activity recreation or native cancellation from those events.

Local abandonment is justified only by actual account/owner/session/activation revocation, or an explicit user action bound to the still-pending request. A route/editor binding reconstructed with a new activation invalidates the old one; a widget rebuild or same-activation rebind does not. Process death has no surviving Dart Future/lease and restores a fresh editor independently. Activity-only recreation with a retained engine may strand the old native Future without any reliable Dart distinction from normal return. Do not infer loss automatically: if original authority is still valid, keep accepting its callback and offer the explicit action below. If reconstruction actually replaced authority, abandon only the superseded request.

Use one small `Interrompi selezione` action beside the existing photo controls, visible/enabled to the current authorized owner while its picker wrapper remains pending. It must remain callable while the feature add Command is running, without waiting for that Command, native retrieval or a timeout, and must not block other editor/local-checkpoint/navigation access. The action abandons the captured nonce, preserves fields/files/resume intent, settles the local wrapper as interrupted (neither successful asset recovery nor native cancellation), and lets normal Command settlement release application admission. It never launches another picker automatically. After settlement the existing Add control permits a separate explicit selection; no new dialog, warning queue or generalized picker state machine is required.

Before local settlement, atomically revoke that request's publication authority; callback completion and abandon have one winner. Late success/error from A is observed but cannot stage/upload, republish an error into B, clear B's navigation nonce, release B's lease or regain authority in A1 → B → A2. The native Future may remain physically pending: do not await it to release the wrapper, do not claim it was cancelled, and do not dispose a still-running feature Command before its wrapper settles. Preserve existing Command error/settlement rules. The gateway owns the native Future's terminal observers even after abandon so a late error cannot become unobserved or alter replacement UI.

Retrieval takes no launch lease and never gates launch. A plugin `already_active` response after local abandon is a settled native rejection, not permission to spin/relaunch; leave the editor usable and the existing Add action available for later explicit retry. Local nonce checks fence callbacks delivered to A's original Future, but cannot prove native provenance if the plugin were to deliver old media to B's new callback. Verify this distinct native stale-delivery/new-launch ordering on device. A demonstrated cross-request native rebind requires a narrowly reviewed prerequisite before affected live intake can ship; do not solve it by guessing attribution, resuming A, adding a timeout or leaving a permanent application lock.
