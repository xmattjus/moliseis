# Design

## Context

See proposal.md for motivation. Baseline is PR #12 head `c6e4a21b17f9d14299f7a159dd7bebe5b31d9af1`, base/main `ee60777c7fdfc5c16daa1151050c134fbb7cde29`; PR open/Draft. The fifteen migrated ViewModels grew from 4,009 to 6,515 physical lines. The three utility files (432 lines combined) are unchanged by the PR, so their complexity is not attributed to this migration. Detailed evidence and measurement definitions are in simplification-audit.md and metrics.json.

`command_it 9.5.2` defers action entry, emits terminal results before synchronous running clears, then clears running again in finally. Catch routes errors through notifiers before global reporting. Assertions bypass normal terminal handling and can strand runAsync. Disposing a live command immediately is unsafe for late raw throws beyond its 50 ms notifier teardown. Source: resolved package `lib/command_it.dart:310–407,429–430,799–825,1011–1025`; existing tests confirm these are concrete constraints. No package upgrade or foundation rewrite is planned.

## Goals / Non-Goals

**Goals:** a developer can trace admission → repository action → terminal publication in one feature file; fewer duplicated snapshots, lifecycle witnesses and test probes; preserve durable writes and current identity; recover reads explicitly when needed.

**Non-Goals:** generalized execution engine, new base ViewModel, shared scheduler, optimistic history reconciliation, cross-owner write serialization, physical cancellation, automatic retry of mutations, broader architectural cleanup or additional hardening. Do not modify the seven historical changes, backend, AGENTS.md, dependencies or shared foundation in this pass.

## Decisions

### D1 — Remove proven duplicate state first (R01–R03)

GeoMap keeps the immutable GeoMapMarkerRequest object and its identity check. Delete its separate ticket and second identity comparison: identical requests necessarily contain the same ticket. Derive markerStatus from markerTerminal (null means loading; terminal failure or outcome.firstError means failure; successful empty/data otherwise). Preserve successful programmatic empty selection and partial source-error semantics. Do not derive from only the last command result: admission clears the owner terminal synchronously before the deferred command snapshot catches up.

Dashboard execution `id`, `token`, `started` and owner `_nextExecution` are unused bookkeeping. Delete them and corresponding constructor arguments/assignments. Retain object identity used by the mutation phase and the method token checked by `_canRead`; the unused stored token is not that authorization check.

These are behavior-preserving changes. No new spec requirement is justified.

### D2 — Dashboard editor return requests a refresh, without a revision obligation (S01)

Keep `refreshAfterEditorChange()` as a small sequential method: if live, request/await one `refreshSubmissions()`; after it returns with a normal terminal snapshot (success or handled failure, not the still-running snapshot left by an assertion), if still live and ignored is selected, request/await `refreshIgnoredSources()`. Existing admission can reject either read when busy; that completes the request without implying success. Keep the existing owner/mounted check in `_openEditor`.

Delete `_editorRevision`, `_editorReadingRevision`, `_editorDrainQueued`, `_editorNeedsIgnored`, `_editorSubmissionRead`, `_editorIgnoredRead`, `_editorWaiters`, and `_scheduleEditorDrain/_drainEditorChanges/_completeEditorRevision`, including wakeups from settlement. No pending-refresh flag replaces them. Do not make a later editor return extend someone else's refresh Future.

Saving already committed before the route returns true. An older dashboard read can therefore leave stale rows after a busy refresh request; manual pull/menu refresh or retry is the recovery. This weakens automatic freshness, never the editor write. Preserve list retention, filtering, terminal error distinctions and accepted ordinary refresh Future semantics.

Keep the separate post-unIgnore mutation/refresh phase, exact pending ID navigation gate and its existing lifecycle protocol. That coordination protects a persistent action plus a specific UI transition; its independent simplification lacks sufficient evidence (N02).

### D3 — Search history: one FIFO of accepted writes, independent ordinary reads (S02)

Keep results/suggestions RestartableCommands and popup ownership guards unchanged. History add/remove becomes confirmed presentation: display the last successfully loaded list until another read succeeds. No speculative add/remove, rollback, base list, projection or rebase. Empty/category-label exclusions remain; case-insensitive duplicate adds and exact removals remain repository rules.

Use the existing two private ordinary command roles: a write command receiving an immutable `(query, add)` record and a read command returning the repository history. One `Future<void>` tail sequences accepted writes. Appending a closure transfers the obligation synchronously, before navigation/notification. That closure captures only repository/command operation inputs; after UI disposal it can execute previously accepted writes but cannot read or publish presentation state. Reject new acceptance after disposal. No queue class, receipt per mutation, drain Completer, execution epoch or detached-writer object remains.

Reads are independent single-flight operations. Bootstrap and `requestPastSearchesRefresh()` each request one read; completed writes can request a best-effort read while live. A busy read request may be ignored, with no queued demand. A slow or indefinitely pending read cannot block the write tail. An older read may publish confirmed but stale history; no immediate freshness promise remains. User-triggered reload or owner recreation recovers it. No automatic read retry loop exists.

The write tail owns persistence independently of presentation, without requiring a separate writer class. The shared disposal rule below gains only an explicit narrow clarification for this existing Search obligation; no other feature may start phases after owner revocation. The write tail waits only for its active write command's completion callback described below. Expected or normally handled raw failure records a visible history failure, then permits the next accepted write. The raw command runtime reports the original error once; the tail must not catch an Object and convert it to Result.error/success. A successful read replaces the confirmed list and clears visible history failure; a failed read retains data and failure. Add a small `Ricarica cronologia` action in the existing empty-input history popup, visible with retained history and on empty/failure, not a new screen. It invokes only read refresh; it never replays a write. While read busy it can show/disable through existing command running state.

#### F1 — Live history subscription in the open popup

At the checkpoint, `app_search_anchor.dart` has two distinct paths: `suggestionsBuilder` materializes `_lastHistory` for empty text, but `_buildViewBuilder` ignores its `suggestions` argument in that branch and renders the cached list in a conditional Recenti section (`:262–282,390–431`). Therefore `notifyListeners()` alone, or a reactive child added only to empty-input suggestions, does not rebuild the actual popup history.

Place one local `ListenableBuilder(listenable: capturedOwner, ...)` in the **empty-input Recenti section of `_buildViewBuilder`**. Keep this reactive section mounted even when history is empty; it contains confirmed chips using the existing Wrap layout, original visible failure, loading and the read-only `Ricarica cronologia` control. The dependency path is: successful read commits the confirmed list and clears failure (or terminal failure retains chips and records the failure) → the live Search ViewModel notifies → this popup-route builder rebuilds from the current confirmed list/failure/read status. Notify for those observable changes even if the list values are equal. Parent anchor rebuilds and text changes are not prerequisites.

Capture owner, SearchController and popup session in the anchor's build-time `viewBuilder` closure and pass them into `_buildViewBuilder`, rather than recapturing replacement-owner fields inside an old popup route. Before accessing anchor State/widget, controller, owner presentation or popup context, require mounted/current owner/controller/session and the empty-input branch; callbacks additionally require the existing `_admits` predicate. Invalidated builders return an inert empty widget; stale callbacks do nothing. Flutter owns the local builder's subscription/detachment when its subtree is replaced or removed. A replacement popup receives its own captured owner/session; old notifications cannot update it. No global listener, event bus or controller notification workaround is introduced.

`_lastHistory` remains a cache of **materialized, inert widget values**, safe for the existing unmounted/stale `suggestionsBuilder` fallback. It must never store the live ListenableBuilder or a subtree that subscribes when returned from that fallback. Construct current chips only inside the guarded reactive builder, using its live popup BuildContext (adjust the local chip helper parameter if needed), and update the inert cache only for that current session. Do not access `State.context` from a late fallback. Keep chip callbacks guarded even on cached widgets. Remove the delete-chip zero-width-text/delayed-reset refresh workaround: confirmation/reload changes the rendered section through the local subscription without editing input or scheduling a synthetic text change. Nonempty result/suggestion latest-wins paths are unchanged.

Rendered acceptance is H10 in test-plan.md, not merely a VM-listener test. It holds the same popup open with unchanged empty text across controlled read success, retained-data failure and read-only reload, then checks owner replacement/unmount and mutation call counts.

One stable write running observer schedules a microtask followed by one event callback when running becomes false. It inspects the command snapshot and completes the single current write waiter after upstream terminal/error processing. This is a local bridge for the actual package limitation, not a scheduler with revision witnesses. Install the active waiter before `.run()`. No next write starts from a results listener. For an assertion (running ends with no normal terminal), preserve the upstream fail-loud path, stop the tail and release eligible private resources; do not manufacture a successful completion or continue queued mutations. Do not promise recovery from a programming assertion; after fixing it, restart the owner. Normal expected/raw failures do continue accepted FIFO obligations.

Retain pending write commands through detach until accepted obligations settle. Idle/settled resources can use the same simple completion boundary for release. Reads retain their existing safe late-throw release guard; do not shorten shared disposal helpers as part of Search simplification.

**Removed state:** `_HistoryWriter`, projection behavior of `_HistoryMutation` (replace only input by a record), `_base`, `projection`, `_known`, `_uncertain`, `epoch`, `_requested`, `_attempted`, `_physicalRead`, `_detached` reader waiter, `_drain`, `_readerTurnQueued` scheduling, mutation settled Completers. Retain a disposed flag, write tail, one current write waiter, a stopped-after-assertion flag, the two private commands, the last confirmed list and one original visible failure value. The waiter acknowledges physical termination, not application success; on missing terminal it resolves coordination while the stopped flag prevents later queued writes. No false domain Result is created. No cross-owner ordering/dedup guarantee is introduced.

### D4 — Editor: fixed commands and semantic captures, no physical execution engine (S03/R04)

Keep eleven fixed private ordinary commands and the existing public `request*` API. Retain the directed conflict matrix: Load excludes all work; mutations exclude other mutations; the established advisory-read/mutation overlaps remain. Keep synchronous admission before notifications and command entry. For a live owner, accepted editor work is not silently dropped or rerun. Unlike Search history, editor admission is a revocable reservation: owner disposal before action entry intentionally skips I/O, as the existing contract requires. Do not collapse all operations into one untyped universal command or add a generic lane replacement.

Remove `_EditorLane` and `_EditorExecution`. Declare typed commands and only the local request captures needed by each action. Immutable records/closures capture draft revision, target ID, source hash, preview token/group, digest/asset ID and candidate/context generations. Actions use the captured values plus `_disposed` and relevant semantic generation checks instead of receiving an execution object. Keep Save's matching clean revision and logical attempt association; do not replace it with a generic `completed` flag.

If disposal occurs synchronously from the admission notification before `.run()`, no running transition will occur. That path directly clears the captured request/reservation and schedules safe idle command release, with no public terminal success and no wait for a completion callback. A `.run()` already admitted but not entered uses the existing disposed guard to skip its action phases.

Each command has one stable `isRunningSync` observer. On completion it schedules the small post-turn boundary used locally above. A reservation remains held until that callback. Read the terminal snapshot there, check current semantic authority, release reservation and publish one terminal outcome together. Publish running synchronously on admission; keep neutral cached advisory snapshots where input changes invalidate command results that are still physically pending. A terminal snapshot is deliberately published later than the current implementation; no wall-clock delay or exact event-count is an application contract.

The completion callback must clear its old local bookkeeping before notifying UI; then it must not clear new reservation/state after a reentrant request. A listener may admit a new request after release; it must execute once and remain busy independently. No admission occurs during upstream terminal dispatch. Preserve the existing synchronous conflict predicate until release. One boolean reservation per operation can cover the gap between command running=false and safe publication; it is not a physical receipt/generation system.

Retain logical once-only effect IDs for the seven UI mutation effects and Save/dialog revision association. These IDs are not physical command identities; do not remove them merely to reduce counters. Screen `_consume` can continue using them, so route/dialog ownership and covered-route behavior remain. No broad screen rewrite is needed.

#### F2 — One effective resource release per private Command

Keep three facts separate: `_disposed` immediately revokes application admission/publication; already-started physical work can still be pending; private resource disposal becomes eligible only after that work settles and the existing post-turn dispatch/reporting boundary has passed. A reservation released after a normal live completion does **not** dispose the reusable private Command.

Use one editor-local identity set of released Commands (at most the eleven fixed commands) and one release function; no lane/receipt object is needed. Every resource-disposal path must go through this function. On entry, return immediately if the command is already in that set, before reading its notifiers, removing listeners or scheduling any more work. Only revoked-owner, physically idle, dispatch-safe commands may reach release. At the effective release point, atomically add the command to the set **before** detaching its stable observer and calling `command.dispose()`. Membership is permanent for that Command and is never reset on completion, reentrant notification or owner cleanup. The set is local idempotency bookkeeping, not an execution engine or a production diagnostic counter.

Both the bulk owner-cleanup callback and the direct skipped-admission cleanup can already be queued for the same never-started command. Either can claim release; the other must become a no-op. A late scheduled completion callback first checks the same set and returns without reading disposed notifier state. For revoked but still-running commands, bulk cleanup leaves resources alive; the retained completion observer releases them once after physical settlement/reporting. For already-settled commands, only the queued safe release is needed. Reentrant disposal and terminal notifications use the same permanent claim. No path may call `command.dispose()` directly outside the guarded release function or detach the same private observer again after effective release.

The never-started admission branch clears only request captures/reservation and schedules that guarded idle release; it never fabricates a terminal success or starts picker/repository I/O. Late handled runtime errors preserve the original Object and stack and report once before resources release; cleanup must not hide them behind a secondary disposal/listener error. Keep E1/E5 and add E11's deterministic convergence trace without restoring the four R04 diagnostic getters. Exact effective cleanup remains required; physical command reuse/count probes are not the application API.

Delete actionSettled/started/settled/queued/revision witnesses, the paired private results/running observers, barrier rescheduling, per-execution action objects, settlement/disposal counters and four debug getters. Replace identity/count-only test assertions with admission, captured repository calls, correct error/success, once-only effect, late-error safety and no next phase after dispose. For assertion aborts, cleanup remains fail-loud and the owner can stop accepting more work; automatic reuse after a programming assertion is deliberately no longer required. A nonterminating action is not declared cancelled.

Keep a small local completion registration function if needed for the eleven typed commands, but it must only bind one observer and detach/release it. No new shared utility, scheduler, generic execution object or revision-based barrier is allowed. If integration would require equivalent receipt machinery, stop that increment and bring a concrete contradiction back for review; do not silently redesign the plan.

### D5 — KEEP and evidence-limited decisions (K01–K06/N01–N03)

Keep Content Submission's admission-time sessions/digests/membership, pre-upload draft checkpoint, lifecycle serialization, staged ownership and remote clientSubmissionId. Confirmed remote success followed by local failure offers finalization-only retry, without upload/final RPC repetition. Keep Auth credential-free command parameters and session-correlation checks before sign-out/anonymous restoration. Keep backend authorization/transaction/replay boundaries.

Keep Event day request/dataset revision authority and Home coalescing, which largely predates the PR. Keep Category synchronous filters, combined immutable retrieval, atomic publication/current sort, and the existing selector mounted-owner/draft guards. Shared disposal duplication and Content Submission forwarding may be reducible, but no proven smaller replacement is included; N01/N03 authorize no implementation task. Do not turn this audit into another hardening migration.

## Effective specification replacement ledger

The canonical `command-execution-concurrency` spec has seven foundation requirements. Most affected requirements below currently exist only as ADDED blocks in pending migration deltas. This change uses RENAMED plus MODIFIED blocks against that **effective post-migration baseline**, not against canonical alone. OpenSpec 1.14.3 parses `FROM: ### Requirement: <old>` / `TO: ### Requirement: <new>` pairs, applies RENAMED → REMOVED → MODIFIED → ADDED, and explicitly rejects MODIFIED under a renamed FROM header. Thus all seven renamed contracts are modified under their TO headers; the other six of the thirteen targeted replacements keep their accurate names. Evidence: installed `dist/core/parsers/requirement-blocks.js:403–440` and `dist/core/specs-apply.js:204–225,305–354,380–402`; the isolated composition script verifies correspondence and scenario preservation. During this planning run no synchronization or archival occurs. Future synchronization must compose the seven deltas first, then this delta; alternatively a separately authorized synchronization can materialize their additions before applying these replacements. Never apply this change first or leave both versions normative. Historical designs/test plans remain provenance, superseded only for the rows below.

## Risks / Trade-offs

- **Stale dashboard/history after a busy read** → existing dashboard refresh and explicit history read reload; no mutation retry is coupled to it.
- **History deletion/addition no longer instant in the popup** → retain confirmed chips with loading/failure/reload; navigation remains immediate; no speculative rollback can erase a later accepted write.
- **Hidden state reappears in a new completion helper** → forbid revision witnesses, nested queues or a shared execution framework; compare field/listener inventory after each increment.
- **Editor admission reopened too early** → one reservation through post-turn completion; reentrant terminal tests verify exact repository calls and stable new busy state.
- **Lost error after disposal** → retain live commands beyond 50 ms until settled; compare original Object/stack and absence of secondary notifier errors. Assertions remain fail-loud.
- **False saved/committed state** → retain Save draft revision and source/preview tokens; never infer persistence from Future completion alone or retry remote mutation on a read error.

No DB migration, feature flag or data conversion is required.
