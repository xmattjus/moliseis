### Backend constraints

Admin Edge authenticates a non-anonymous user with `app_metadata.admin == true`; create derives user ID/email/name server-side. It inserts through Admin store without `client_submission_id`. Public's `(user_id, client_submission_id)` unique key and transactional replay RPC do **not** protect Admin create. A lost response may leave an unknown committed row. Asset association locks the parent, requires pending status, and enforces at most five in one transaction; it has no association idempotency key. Admin moderation is authorized across submissions, so local draft owner means editing account, not necessarily remote contributor. Update responses do not contain the complete associated-assets envelope. Never replace confirmed assets from an empty update response.

Local foundation needs no backend addition. Exactly-once Admin create/association would require a separately reviewed backend contract; Plan 2 cannot infer it from local identity.

## Goals / Non-Goals

Provide one active Admin editor with durable, isolated recoverable checkpoints and local files; guarantee safe attribution of recovered picker results across Public/Admin; keep remote readiness distinct from local durability. Introduce only two Admin persistence boundaries and one small shared picker ownership/handoff boundary.

No automatic draft autosave, cloud draft sync, generic session/media manager, remote replay, create-ID adoption, staged upload Save, progress route, post-Save navigation redesign, dirty-exit dialog or remote conflict-resolution UI. New-mode photo selection remains disabled. Internal staging seams are intentionally ready for Plan 2, not end-user staged Save functionality.

## Decisions

### 1. One active editor; preserve recoverable sessions by account and target

Use one application-level `AdminSubmissionEditorViewModel` supplied by the existing Provider composition root. Activation explicitly names `(adminUserId, new | remoteSubmissionId)`. A new target resumes that account's recoverable new draft; an existing target resumes its checkpoint if present. Durable lookup has at most one resumable row per `(account, target)`; fenced historical new sessions can be parked under their own session key, preserving them outside that resumable target slot; `new` is an explicit target discriminator, never a fake remote ID. Previous remote targets and other accounts remain on disk. Technical duplicates are an unavailable/repair condition, not permission to arbitrarily select or delete a user's checkpoint.

Fresh activation generates a secure UUID v4 local session ID without a write. Reopening the same target during this process reuses the current session, including uncheckpointed fields. Route detachment removes effect authority; it does not destroy or implicitly save the application owner. Switching to a different target is refused while fields differ from the local checkpoint, while a local mutation is settling, or while remote mutation/picker work is active. Present a small inline activation error with a return-to-current-editor action; the current editor offers an explicit, clearly local checkpoint action. No new exit dialog and no automatic save-on-switch. After checkpoint succeeds, switch may proceed; a checkpointed but remotely dirty session is safe to leave and remains recoverable. A fresh untouched session can switch without storage.

Auth revocation overrides switch admission: immediately detach/revoke the active generation, cancel upload best-effort, clear private UI state, and retain durable account-owned work. Uncheckpointed fields may be lost on logout/process death; explicit-only persistence deliberately does not promise otherwise. Another account never receives the old memory. Reauthorizing the original account requires fresh explicit activation and a new generation.

Rejected: route owners lose activity-recreation state; one destructive disk slot deletes useful sessions; general multiple-live-editor management adds no required capability. No TTL/LRU deletion is introduced. Disk retention across accounts is intentional application-private persistence, not encryption or protection from a compromised device.

### 2. Immutable snapshot, checkpoint and remote truth are separate

`AdminSubmissionDraft` identifies `localSessionId`, `adminUserId`, optional existing remote ID and immutable editable fields. Fields are nullable category/city/name/description, recursively frozen Delta, full `EventDateDraft`, and exact latitude/longitude strings (including whitespace, comma, half-pair, non-finite or invalid text while editing). No validated-input coercion occurs on checkpoint. The replay fence and checkpoint sequence are lifecycle metadata, not editable fields or snapshot dirtiness. Snapshot equality is deterministic structural equality including identity and every editable value; no setter dirty flag is needed for local dirtiness. Transient dialogs, errors, search candidates, merge previews, source acknowledgements, commands, progress, contributor display metadata and loading state are excluded.

The VM maintains current snapshot and last confirmed local checkpoint separately. Persist one checkpoint snapshot, not a redundant copy of an arbitrarily newer in-memory current value. A restored snapshot is its local baseline. A genuinely untouched session starts equal to a provisional baseline and absent on disk. Explicit ordinary checkpoint is a no-op for that untouched state, and for an equal **known durable** snapshot. Picker preparation explicitly requests durable existence, forcing the first write even if equal. A dirty checkpoint captures A inside arbitration and writes A; later current B remains locally dirty. Failure preserves the old baseline. Unknown storage blocks checkpoint/picking rather than overwriting unread state.

Existing remote Save/moderation readiness remains a separate projection: local checkpoint never clears remote dirtiness, establishes loaded status or authorizes moderation. Preserve `isDirty` semantics for remote guards and expose local `hasUncheckpointedChanges` separately. Existing empty new editor remains remotely clean until changed. Retained staged assets block moderation and any Save path incapable of persisting them.

For edit targets, checkpoint incomplete fields as well as a narrow immutable remote baseline: server-projected editable fields, status and `modifiedAt` observed from successful detail load (source tokens/previews still fetched, not trusted from disk). Do not persist the entire remote detail or contributor PII just for symmetry. Baseline uses server numeric coordinates; compare projected valid draft coordinates semantically so server `41.0` versus raw `41,0` is not a spurious remote edit. Invalid text is always remotely dirty. Keep raw strings exact in the local snapshot.

### 2a. Keep legacy Save while preventing resurrection of completed new drafts

This is a required local lifecycle correction, not the staged remote Save workflow. Existing `admin_submission_editor_commands_test.dart` explicitly permits changing B during Create A and then issuing Create again. With a durable new draft that behavior can resurrect an already-created submission after restart. Correct it narrowly: synchronously reserve the new session at Create admission and lock both editable fields and checkpoint/durable-owner writes through settlement, while preserving Update's A/B behavior. Capture existing durable-existence knowledge inside local arbitration before the remote call. A pending earlier checkpoint must settle before deciding whether a fence is required; a later checkpoint request is refused while the Create reservation is held. Thus a non-durable Create cannot acquire an unfenced row midway through the request. Setters and admission reentrancy obey the same lock; the screen reflects it. A duplicate Save after confirmed Create is inadmissible even if the route was covered and could not pop. No returned remote ID is adopted into editor mode or stored as a target.

Before invoking legacy Create for an already-durable new session, mark that exact row `createAttempted` under local arbitration. Failure writing the fence prevents the remote call. Do not create a draft row solely to fence an untouched/non-durable session; there is no disk draft to resurrect. After any attempted Create with an uncertain result, keep the durable fence and prohibit another Create from that restored session. Preserve fields/files with an explicit outcome-needs-verification message; Plan 3 or a subsequent backend contract must resolve it. That message offers an explicit local **start separate new draft** action: park the fenced historical row under its own session key, atomically release the account/new resumable slot, then create a fresh in-memory identity with no write. Do not delete the old checkpoint or attach its assets to the new session. Explain that the earlier remote outcome is unknown and a separate submission may duplicate it. If parking fails, keep the old session active. This is local session selection, not retry, ID adoption or stale-outcome resolution; Plan 3 owns reopening/resolving parked history. It prevents one uncertain attempt from permanently disabling all new work for the account. Pre-admission validation failures make no remote attempt/fence. This intentionally narrows retry admission for a durable ambiguous new draft; it cannot prove the first insert committed. Non-durable live failure retries retain the current backend limitation and make no exactly-once claim.

On confirmed Create success, logically complete/seal that runtime session, retire its exact durable row, and clean only its owned staging/inbox. Preserve current successful route-pop semantics after required local retirement; a covered route must not regain Create admission on return. If local retirement fails, expose local-finalization failure with a **local-only cleanup retry**, never repeat Create. The persisted fence survives restart and prevents replay. A crash before fence commit starts no remote request; a crash after fence commit but before the remote call conservatively leaves uncertain state. This false uncertainty is accepted because the current API offers no replay lookup. New mode cannot Save with staged assets; no create/upload bridge is smuggled into Plan 1.

For successful legacy Update A, advance only its confirmed remote baseline; B typed in flight stays remotely dirty and prevents the old success from closing. Reconcile pre-existing durable checkpoints under local arbitration: Save admission captures the local checkpoint sequence; confirmation may retire the old checkpoint if no newer explicit checkpoint was committed. If a newer checkpoint B committed during Update, retain B and update only its remote baseline to A, without marking B remotely clean. Do not autosave the current in-memory B. Local baseline/durable-existence state changes only after the corresponding local operation succeeds. A local persistence failure after confirmed Update is reported as local-finalization failure and repaired locally without replaying Update; process death before that local repair leaves an old checkpoint that restoration safely blocks against the fetched changed remote baseline. Existing immediate asset mutations never clear field checkpoints or pretend to confirm fields.

Same-generation auth revocation still permits an already-started repository-local commit to finish for its captured owner, but not UI publication or new remote phases. On reauthorization, a Create fence remains unavailable for ordinary Create even if its successful response was suppressed. This does not provide remote idempotency, persistent ID adoption, automatic result reconciliation or a progress route.

### 3. Initialization respects both local edits and freshly fetched authority

Application startup initializes the picker coordinator eagerly, independently of opening an editor. Admin target initialization begins on activation; concurrent callers for that exact account/target/generation share its one future. Different target requests do not retarget a waiting future. Expose loading, ready, unavailable and blocked-remote-context states explicitly.

Sequence: validate current account/privilege → resolve durable target lookup → bind restored or authoritative-absent session → reconcile that session's staged descriptors → obtain remote detail for edit targets → publish one coherent ready outcome if generation still owns it. Unknown draft reads or malformed/unsupported rows preserve bytes/descriptors and prohibit null-owner reconciliation. A failed staged load never exposes partial runtime files. Explicit retry creates one new shared attempt after failure, not concurrent reloads.

A restored dirty checkpoint keeps its editable fields and old confirmed remote baseline. Fetch latest remote detail for status/assets/validation context. If the server's editable projection/status/version equals the saved baseline, use it and retain local fields as remotely dirty. If a checkpoint is remotely clean, fresh remote detail may hydrate the editor without an implicit local write. If remotely dirty baseline diverges, remote is missing/final, or fetch fails, keep checkpoint recoverable and show it read-only with normal error feedback; block Save/moderation/immediate asset mutations. Plan 1 detects a context it cannot safely use; Plan 3 supplies discard/rebase/reload/merge recovery UI. A later retry can enable it only if the original baseline still matches. `modifiedAt` is a conservative detection hint, not a compare-and-swap guarantee; new races after fetch remain the existing server contract.

A load completing after in-memory edits may update authority only if captured draft/session revisions still match; never overwrite later local fields. Remote final status always governs editing eligibility. Local asset state is not evidence the remote row is still pending.

### 4. Additive ObjectBox entities; no replacement database

Add `AdminSubmissionDraftEntity` (auto technical ID, indexed unique validated lookup key (account/target for resumable rows, account/parked/session for retained fenced history), local session ID, owner ID, nullable remote ID, versioned checkpoint/remote-baseline payload, checkpoint sequence and local Create replay fence), `AdminSubmissionStagedAssetEntity` (auto ID ordering, owner/session, digest, canonical relative path), and `PickerRecoveryEntry` (auto ID, unique ticket nonce, feature/owner/session, optional remote target, active/revoked/settled marker, versioned committed inbox descriptors). These are proposed symbols, not existing APIs. Use explicit codec validation; malformed payload differs from absent row. Prefer JSON only for cohesive snapshot/manifest payloads; query ownership columns remain explicit. Do not add separate active-session pointer entities, generic journals or remote operation queues.

Repository draft contract: load by owner/target returning absent/valid/error; write captured snapshot/baseline for exact session; retire exact owner/session; preserve other targets. Stage contract: acquire, reconcile/load exact owner/session, structurally resolve, remove by owner/session/digest, clear exact session. No Admin `reconcile(null)` cleanup-all API. Critical same-store retirement changes can use a transaction owned by the data boundary; UI never composes raw Boxes.

Generate IDs/UIDs with the established build_runner workflow **during apply only**. Existing IDs/UIDs, retired UID lists, schema version semantics, fixed Public row and store directory stay intact. New entity/property/index UIDs are generated, not prescribed or reused. Test opening a pre-change populated store and ensure Public/settings/content/cursors survive. Unsupported new payload versions quarantine the row without rewrites. A release rollback must use a schema-compatible build; do not promise destructive schema rollback or downgrade compatibility without testing it.

### 5. Stage Admin bytes under a separate root with explicit owner scope

Root is application support `admin_submission/staged/<account-uuid>/<session-uuid>/<sha1>`, relative to the Admin staging root; validate canonical UUID keys before path construction. Public remains `content_submission/staged/<clientSubmissionId>/<sha1>`. Picker inbox has its own `picker_recovery/<ticket-nonce>/` root. Neither feature's cleanup scans the other's root.

Use Public's current SHA-1 accidental deduplication and limits (`kCloudinaryMaxUploadBytes` = 10 MiB, `kMaximumSubmissionAssetCount` = 5). SHA-1 is not an authenticity/security primitive. Acquire: verify ownership/capacity/source size → digest → existing-session duplicate detection → unique temporary copy → close/flush → verify final size/digest → same-directory final rename → descriptor put → runtime publication. Do not expose partially written bytes. Descriptor order is explicit ascending auto-ID; reselecting a duplicate does not reorder it. Capacity is fetched associated count plus valid staged descriptors, checked again inside local arbitration; backend remains authoritative for concurrent remote additions. If freshly fetched associated assets plus restored staged descriptors exceed five, preserve every valid committed local file and show an over-capacity state. Block new selection, legacy Save and moderation until local removal brings the total into range; do not truncate staging to meet capacity. Exact-session local removal remains available even when remote context is blocked. No remote digest exists for associated images, so do not claim byte deduplication against remote URLs.

Reject absolute, traversing, noncanonical paths, wrong owners/digests and symlinks at root/account/session/file segments. Enumerate with links disabled, unlink contained links rather than following them, never delete external targets. Validate digest/size at acquisition and reconciliation; subsequent resolve is structural, matching Public. Containment checks are defense against persisted corrupt paths and pre-existing links, not an OS-level guarantee against a hostile process racing filesystem syscalls.

Reconcile only a verified session: retain lowest valid duplicate descriptor ID, remove malformed descriptors by technical ID, remove missing/corrupt/oversized descriptor-backed entries, delete contained temporary and descriptor-less files best-effort. Never reconstruct orphan files. Invalid individual entries do not invalidate valid committed siblings; a hard store/read/write failure produces unavailable state without publishing a partial list. Failure is not absence and never authorizes broad cleanup. A stage failure later in a batch preserves earlier descriptor-backed commits.

Remove descriptor first, then contained file; missing file is success. If descriptor removal fails, preserve runtime state; if bytes cleanup fails after descriptor removal, report path-free cleanup feedback and leave non-restorable residue for reconciliation. Explicit retirement first deletes/marks the exact durable owner, then cleans that session and rotates memory; failures before durable retirement retain identity/baseline. Foreign valid sessions are never orphaned merely because inactive. Global Admin orphan sweeping is excluded: targeted cleanup may follow authoritative absence of that exact session only; unknown account inventories/unsupported rows remain quarantined. This small policy trades disk residue for safety.

### 6. One shared picker coordinator owns retrieval and launch attribution

Add one concrete application service with a narrow injectable picker seam and persistence implementation. It is not a feature draft repository, upload controller, moderation service or generic media framework. Create it from startup after bindings and ObjectBox open, before `Supabase.initialize`/anonymous-session setup and before editor routes can launch pickers. Start acquisition there; expose its shared completion future through Provider. Move ObjectBox open and coordinator acquisition ahead of the existing awaited auth setup, preserving setup-error behavior when ObjectBox cannot open. Lazy Provider construction alone is insufficient.

Coordinator startup: read ticket/inbox ownership first → on Android attempt `retrieveLostData()` once for this process startup lifecycle → acquire returned bytes immediately into inbox if a valid unrevoked ticket exists → publish handoff availability independently of auth or route. Concurrent Public/Admin recovery requests await the same attempt, including empty/error outcomes. A retrieval exception establishes unknown native consumption and blocks new launches for that entire startup; retain original attribution and allow already-committed inbox delivery only. A successful empty response with **no surviving active ticket** permits launch. A successful empty response with a surviving active ticket does not prove the former external activity has settled: mark its lease unresolved and refuse replacement launches, retaining the old ticket. A later startup's attributable nonempty terminal recovery or the original live callback can settle it. Do not fabricate cancellation from empty retrieval or add a second platform attempt in this startup. On non-Android do not call the lost-data plugin API; after process recreation, invalidate surviving old launch tickets without delivering media and allow normal fresh launch/cancellation under ownership guards. Android unresolved-native-cache blocking does not apply to those platforms. Existing committed inbox items, if any, still require ordinary owner verification. No recurring lifecycle observer retries retrieval on every route/resume. Existing durable inboxes are retried without another platform call.

One global picker lease covers actual platform interaction. Every launch waits for startup acquisition, verifies feature durable owner, persists a fresh random ticket with feature/session/account (Admin) and exact remote target if present, then launches. Failure writing checkpoint or ticket prevents launch. Reserve synchronously before notifying, recheck after awaits. Never hold the feature local queue during the external interaction. On return, validate lease/ticket, session generation and feature; normal cancellation clears that exact ticket and releases the lease without dirtying assets. Unexpected platform errors retain normal feature error semantics. No new picker overwrites a pending ticket; cancellation/revocation does not release the physical lease until the original call settles (or attributable terminal recovery on a later startup settles it). This avoids attributing an old result to a new ticket. Only a successful startup result with no unresolved former interaction authorizes a new ticket; a crash between ticket-write and launch therefore cannot reassign an undrained older response. If that crash leaves a ticket but no platform interaction, the plugin cannot distinguish it from an unfinished interaction. Plan 1 deliberately leaves further picker launches blocked rather than guessing; this can persist across empty startups. No destructive app-data reset, timed expiry or unverified abandonment action is offered as recovery. This is a concrete availability limitation of fail-closed attribution, including cancellation whose callback was lost. A later separately reviewed native/plugin settlement contract is required for a safe abandon/reset control; it is not silently added here. Normal live cancellation remains harmless and releases its lease.

Normal live results go directly back to the originating feature under that feature's local arbitration. They are not recovered background work and preserve existing live Admin immediate upload/association. Stale results create no feature staged files, descriptors or feedback. Revocation during a commit prevents runtime publication/new phases; already committed owner-scoped work remains recoverable.

### 7. Persist a small inbox because auth and routes may be unavailable

A ticket alone plus cached plugin paths is insufficient: plugin retrieval consumes the cache and cache files are temporary. Each ticket row can contain at most five committed inbox file descriptors (relative path, digest, stable ordinal, bytes count) and a terminal response/error marker. No arbitrary metadata or original plugin path is persisted. Validate candidate count/size and copy each response file with the same temp/verify/rename/descriptor ordering into the private inbox. Sort recovered candidates by digest for a deterministic recovery order because Android native cache does not preserve original selection order; normal selection preserves its supplied order. Deduplicate within the ticket. Earlier committed inbox items survive a later copy failure. Inbox descriptors authorize replay; descriptor-less inbox files are not reconstructable.

Delivery requires exact durable feature/session ownership and, for Admin, restored authenticated account and privilege plus remote context readiness. Absence or unknown local loading never attaches bytes to fresh state. With auth not yet restored, retain inbox bytes. If a different account is active, hide/retain the original account's inbox and do not auto-activate its editor. Only explicit matching target activation under the original authorized account can consume it. A live logout/privilege revocation invalidates its pending ticket immediately; uncommitted later results are rejected. Already durable inbox items remain private/quarantined and require explicit matching reactivation, never a convenience reassignment. Explicit discard/retirement terminally invalidates that ticket/session; delete only its inbox bytes best-effort.

Public automatic consumption after matching initialization uses its existing common pipeline and `_lifecycleTail`. Preserve its clear/retirement/disposal invalidation. A recovery caller in another feature cannot consume the inbox; that feature's activity is irrelevant. Migration data with no trustworthy ticket is dropped with a path-free diagnostic, never assigned to whichever editor opens first.

Admin recovery **never uploads or associates remotely automatically**, including an interrupted persisted-image add. It stages into that same verified Admin session and exposes a local recovered-asset notice with local removal; with staged recovery present, legacy Save is blocked with explanation because it cannot finish that asset work. Plan 2 enables explicit remote persistence. New-mode asset selection stays disabled; an internal pre-create staging seam has no user-facing incomplete Save. A normal live picker in an existing pending editor still uploads immediately. These are distinct semantics required to avoid unsafe replay after process death.

Explicit local asset removal first awaits the shared startup **acquisition-only** future outside feature arbitration (never waiting for feature delivery), so no startup inbox copy can commit afterward. It then enters feature arbitration and must persist terminal rejection of every currently committed inbox item for the captured feature/account/session/digest, then remove the feature descriptor under feature arbitration. Failure recording rejection aborts removal before descriptor deletion; successful rejection followed by descriptor-delete failure leaves the existing staged asset valid for a removal-only retry. A delivery that captured an item before removal must recheck its persisted pending/rejected state inside feature arbitration immediately before staging; a captured reference alone never authorizes commit. A delayed delivery acknowledgement uses compare-and-ack and cannot undo terminal rejection. This prevents ack-failure → user remove → restart from resurrecting an explicitly removed image; digest dedup alone is insufficient once the descriptor is deleted. Coordinator rejection/ack calls here are bounded persistence-only operations and never call back into a feature queue.

For each inbox item, feature descriptor commit precedes inbox acknowledgement/deletion. A crash between the two replays to the same session; digest dedup makes it idempotent. Ack failure leaves the inbox retryable. If owner is revoked/discarded during delivery, no new feature commit starts; any already committed file remains with its original owner. Do not reverse dependency order by calling feature queues while holding a coordinator persistence lock: reserve/capture ticket, release coordinator lock, await feature, then compare-and-ack exact ticket item. No feature→coordinator→feature lock cycle.

### 8. Extend the existing VM and local ordering; do not build a session framework

Keep Admin command orchestration in its VM; extract only the small immutable draft snapshot/codec boundary and shared picker service already justified above. A feature-local future tail, matching Public, orders checkpoint, staged commit/removal, activation/retirement and inbox consumption. Repository calls return `Result` for expected storage failures and release the tail in `finally`; a thrown programming failure is not silently converted to success. Remote requests/external picker time remain outside the local tail. Synchronous command reservations, physical running witnesses and delayed terminal release continue to own admission and late Command settlement.

Each operation captures `(account, localSessionId, activationGeneration, target, effectId)` and immutable input at admission. Recheck after every await and before each publication/next remote phase. Account loss revokes immediately even if physical operations continue. Session A → B → A has a new generation, so original A results cannot publish into reopened A. Clear rendered controller/command effect bindings on generation changes, even though the Provider VM object is identical. Widget callbacks bind exact session/generation/digest, not mutable list indices. Source acknowledgements/candidates/previews reset on activation; current revision guards still apply within a session.

Route binding uses explicit activation outcome, loading/error presentation and session/generation keys for controlled field hydration, not recreation of the application owner. Route effects require a current route binding plus matching execution/generation; reopening a route never replays historical terminals. Covered dialog behavior and existing Save-success/Reject/Promote effects remain until Plan 2 deliberately revises Save. Application disposal revokes the owner and defers physical Command disposal until settlement; command_it 9.5.2's late-throw limitation still forbids disposing running internal commands prematurely. No generic `catch Object => Result.error` workaround.

## Risks / Trade-offs

| Failure window | Required response / accepted limit |
| --- | --- |
| Draft read fails | Unknown, no reconciliation-as-absence, checkpoint, picker or broad cleanup; explicit retry only. |
| Stage copy or rename fails | No descriptor/runtime item for that candidate; previous commits survive. |
| Final rename before descriptor | That uncommitted attachment may be lost; clean orphan, never reconstruct. |
| Native retrieval clears before inbox commit | Process death/disk failure may lose all not-yet-inboxed media. There is no plugin acknowledgement to close this gap; do not claim exactly-once or guaranteed recovery. |
| Crash after some inbox commits | Restore those committed items; remaining response items may be lost. No descriptor-less reconstruction. |
| Crash after feature commit before inbox ack | Retry only same owner; digest dedup; then ack. No duplicate feature item. |
| Empty/error startup with surviving picker ticket | Do not overwrite attribution; further picker launch remains blocked until attributable terminal settlement. Lost cancellation may require a future native settlement contract; no automatic expiration. |
| Auth unavailable/other account | Inbox retained private and inaccessible; no automatic activation/upload. |
| Auth/session changes during work | Revoke publication/new phases; in-flight local commit can finish for original owner, remote request may already commit. No rollback. |
| Remote row changes after load | Existing API has no field CAS; Plan 1 detects restoration mismatch only. Plan 3/backend work must not be implied as completed. |
| Cleanup failure | Retain contained residue, path-free diagnostic; never broaden deletion to compensate. |
| Descriptor duplicates/corruption | Deterministic lowest valid descriptor; unknown draft payload stays quarantined rather than deleted. |
| Device storage retention | No quotas/age policy for all historical sessions in this plan; only exact-owner cleanup. Bounded per-picker payload, not an invented global disk guarantee. |
| Normal live persisted Admin selection already returned by plugin | Preserve immediate path: death before remote association may lose that uncommitted selection. It has no automatic replay or promise of durable staging; only committed recovery/staged copies have the local recovery guarantee. |
| Uncheckpointed typing/process death | Lost by design; no autosave promise. Explicit local checkpoint and pre-picker durability define the guarantee. |

Flush/rename/ObjectBox commit ordering protects process-interruption behavior under normal filesystem guarantees; it is not a distributed transaction or a guarantee against hardware power loss, OS cache eviction before acquisition, storage corruption or hostile same-process filesystem races.

## Migration Plan

Implement additive domain/storage first; verify real-store upgrade before wiring application lifecycle. Add coordinator/ticket/inbox and eager startup before removing Public's direct plugin consumer. Both features must use the shared launch boundary in the same release; leaving even one untracked launcher invalidates attribution. Legacy plugin results without tickets are intentionally unassignable. Public draft/staged data must restore unchanged.

Then wire Admin activation/checkpoint and minimal notices; keep create photo UI disabled and legacy remote workflows. Release only with cross-feature regressions and platform smoke checks. No backend deployment/migration. Do not archive the old change as implemented; preserve it pending the disposition below. This foundation is not independently release-ready: unresolved native picker settlement and deferred staged Save are explicit product limitations for review. Definition-only PR contains only these artifacts; application requires new authorization.

## Verification design

Reuse/extend the existing tests listed in `tasks.md`, shared `FakeImagePicker`, fake repositories/Command harness and real temporary ObjectBox stores. Deterministic Completers establish interleaving/admission/revocation; real files/stores establish copy/commit/reconciliation/upgrade behavior. New tests must follow `molise-is-test-support-reuse` and ObjectBox test-store skills during apply; no duplicate fake Boxes or UI-dependent persistence fixtures.

Automated tests can inject retrieval/copy/ack interruption and reconstruct services/stores, but cannot prove Android process killing, plugin delivery timing, iOS permissions or macOS sandbox behavior. Manual Android activity recreation and process-death tests are distinct (developer “Don't keep activities” is not proof of full process death); test delayed auth, both cross-feature directions, cancellation, offline restart and normal persisted-image actions. iOS device and macOS smoke tests verify picker/cancel and non-Android retrieval no-op. Actual unexecuted device checks remain explicit release limitations.

Documentation audit retains portable decisions, sources and verification summaries in the change. Do not commit raw logs, analyzer dumps, machine paths, temporary manifests, generated verification files or claim planned tests passed. Inspect staged and unstaged whitespace checks and a full changed-file allowlist before publication. Independent adversarial review is required before application; CLI validity alone is not approval.
