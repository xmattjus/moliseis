## Goals / Non-Goals

**Goals:** Own each UI effect by the current route visit, account authority, object owners and selection; keep accepted physical work independent from that presentation lifetime; make recovery actionable without durable side effects.

**Non-Goals:** New navigation architecture, state management, notification widget/framework, remote read authority, persistence redesign, error reporter or synchronization dependency. Backend contracts and existing editor/media behavior remain untouched.

## Decisions

### A1. Explicit Back with normal pop and Home fallback

Use the existing `CustomBackButton` in the main dashboard SliverAppBar. Its callback checks current dashboard route/owners, then uses GoRouter `canPop`/`pop`; only if no previous route exists does it go to `RoutePaths.home`. Do not use the component's unconditional default Navigator pop at a direct root. Rapid repeated callbacks must no-op once the captured route is no longer current. No logout is involved.

Preserve Settings' existing push and Login replacement. First strengthen actual `buildAppRouter` tests: capture the actual Settings Navigator route and meaningful user state (such as scroll position where its lifecycle requires retention), enter Admin from its real tile, and prove Back reveals that preserved route and state. Element identity may supplement these assertions where stable; it is neither mandatory nor the sole correctness criterion. Enter Settings above a real ancestor and prove a second Back returns to that ancestor. Exercise dashboard AppBar and system Back separately. At direct dashboard root the explicit control falls back to Home; platform system Back keeps its normal root-exit semantics. Do not add a root PopScope just to intercept OS app exit. Router/Login changes require a demonstrated failing stack regression, not a precautionary redesign.

### A2. Recovery eligibility and ephemeral suppression

Dashboard State owns only presentation state, not the draft. Lookup occurs after first frame when the dashboard becomes current, after editor/covering-route return, after a new authorized account/owner binding, on an explicitly admitted manual refresh, and before restoring recovery after the ordinary notification tail settles. There is no repository polling or build-triggered lookup. Bind/unbind owner and auth listeners on replacement/disposal; observe route currentness through the existing router delegate Listenable plus ModalRoute dependency, including pushed covers. Coalesce current equivalent lookup triggers or invalidate by a monotonically increasing lookup generation; only the latest authorized completion can publish.

Capture owners, repository, router, route and auth authority before awaits. Track an auth generation as well as account ID so A→B→A cannot revive A1. Revalidate mounted status, provided and widget owner identities, disposal, exact route/currentness and generation before every effect. A route becoming covered revokes pending effects immediately even while the widget stays mounted. Capture safe resources before awaiting; follow the required `if (!mounted) return;` idiom before accessing State.context or State.widget afterward.

Candidate identity is `(accountId, sessionId, submissionId, requestNonce)`. Require successful non-null lookup, matching account and non-null navigation intent; do not display based on repository configuration, ordinary draft or cached stale candidate. Successful null invalidates the current presentation. Error means unknown: retire actionable recovery and preserve disk truth. Automatic eligibility failures produce no unsolicited Snackbar or absence claim; preserve existing diagnostics and their reporting owner without duplicate unexpected-error reporting. Retry only on the established triggers above, without polling or unbounded retries. An explicit `Riprendi` revalidation returning `Result.error` shows the existing generic custom error once, only while its captured authority remains live; it never navigates or deletes durable recovery data. Successful absence silently retires the obsolete candidate. A successful different identity retires the old action and may independently offer the new candidate under live authority, without an error or silently retargeting the click. No “nothing to resume” success message is needed.

Suppress equivalent candidates for the retained dashboard visit after explicit close/swipe or verified successful editor activation for that recovery attempt, never merely route admission. Ordinary feedback only temporarily interrupts presentation and never records dismissal. Action activation blocks duplicate clicks, presentation and navigation during revalidation and the pushed editor visit. A lookup failure releases the latch without automatic re-presentation, permitting retry on a later established trigger. Admission keeps the attempt in progress, not successfully recovered. Failed editor activation, including after admission, records no success suppression: return releases the attempt and rechecks the same durable candidate. Keep a small visit-local set of candidate identities; no disk flag or new repository method. Different nonce/target/session is independently eligible with at most one active presentation. Covering the route preserves that set; leaving/disposal or auth/dashboard/repository owner replacement resets it for the new authority. Thus A can reauthorize later, and a new dashboard visit can offer an unchanged durable intent again. This intentionally does not remember dismissal across visits or process death.

Use the proposed Italian message `Hai una modifica interrotta da recuperare.` and action `Riprendi`. On action, synchronously latch single-flight recovery and revoke its notification, then re-run the authoritative lookup. Keep visit-local dismissal and verified-success suppression separate from this in-flight latch; retain explicit dismissal independently and never add success suppression at route admission. Navigate only if the exact captured candidate still matches and all authority remains live; if a different candidate arrives, never silently retarget the click, but reconcile that new candidate independently. Pass the restored session query and correct new/remote target through existing routes. Preserve editor activation/target validation and exit policy. Actual return to the owning Dashboard is the return trigger; imperative push completion is neither required nor proof of editor activation or restoration. On return, first reconcile the matching recovery attempt using fresh dashboard presentation authority; an old covered-route notification callback gains no authority. Reuse the existing application-provided `AdminSubmissionEditorViewModel`, captured before navigation and rechecked for owner identity, together with the fresh account/session/target/nonce-qualified lookup. Its public `activation` plus `isActivationCurrent(token)` and matching token-owner account/session/target establish an initialized, non-revoked session; a token, session ID, durable-draft flag or pop result alone does not. Only a matching admitted attempt with this initialized-session proof may enter visit-local success suppression. If activation failed or proof is missing, release the attempt without suppression and allow the still-valid undismissed candidate to be offered again. A successful existing editor `Riprova` retry can establish that same proof, avoiding a redundant offer on return. No listener needs to publish dashboard effects while covered; do not inspect private route State or add cross-screen activation events, flags or another state manager.

The distinction follows existing code: `AdminSubmissionEditorRoute._activate()` awaits `viewModel.activate()` after route admission and renders error/`Riprova` on failure. `AdminDraftSession` only validates an activation when its state is ready; the ViewModel also rejects revoked/disposed authority. Activation preserves the navigation intent even on success, so return-time lookup alone cannot distinguish failure from success. Existing picker terminal cleanup owns nonce compare-and-clear; do not move or duplicate it. Route denial, activation failure and retry never consume intent, delete checkpoints, Save or upload. Successful lookup absence or a changed nonce retires the obsolete candidate independently of UI suppression. A change of captured candidate account/session/target or editor/dashboard/repository owner revokes the attempt; a stale return cannot suppress or revive anything even after A→B→A. Continue the existing best-effort dashboard refresh regardless of editor boolean result.

An already-initialized exact account/session/target is a successful reuse, not a failed activation: `AdminSubmissionEditorViewModel.activate` takes its same-session path and `AdminDraftSession.initialize` returns success without repository I/O when ready. Requiring a changed activation generation would reject that valid reuse. Explicit candidate lookup failure exits before navigation and cannot reach success suppression. In the pinned GoRouter 18.0.2, `Block.stop()` restores the current configuration without completing the imperative push Future. Recovery must therefore receive rejection independently of editor return: a one-shot `AdminEditorNavigationAdmission` travels as the individual push's `extra`, qualified by its exact destination URI/session. The existing `AdminSubmissionExitPolicy.onEnter` resolves it after its unchanged synchronous or asynchronous decision, on both Allow and Block; only Block invokes rejection cleanup. No registry, listener, timer, polling or duplicated checkpoint policy is needed. Rejection releases only that captured recovery reservation and matching editor-attempt token, without success suppression, dismissal, durable writes or an automatic retry. Cleanup checks mounted status and exact attempt identity; it can retire its own reservation after authority revocation but cannot release a replacement attempt. A later established lookup trigger may offer the same candidate. Admission still does not establish route commit or initialized editor activation. Ordinary callers retain their original policy result and timing. The real-router regression “ready exact session admits recovery without a replacement activation” verifies this distinction, retained initialization authority and unchanged durable recovery evidence under configured read/reconciliation failures.

### Minimal extension of the existing Snackbar helper

Keep all construction/styling in `custom_snack_bar.dart`. Add opt-in `persist` and native `showCloseIcon` parameters with existing defaults (`false`); native close uses semantic foreground color and native localized accessibility. Preserve custom action colors and render the action exactly once in all text-layout branches, including long single-line text and native close width. Do not create another Snackbar widget.

A raw returned native controller is insufficient for queued recovery, as verified above. Extend this same helper with an idempotent cancellation callback for one owned persistent request and dismissal/resumption callbacks. Retain only the current native recovery controller, the latest ordinary tail/settlement generation and one pending-or-visible recovery request. The dashboard retains candidate, dismissal and authority ownership; the helper coordinates only native presentation. Reuse native queue ordering and `closed` futures, not a second queue, timers, polling, notification service or durable registry.

- Ordinary calls keep finite duration, native queue order and explicit `replaceCurrent` behavior. Suspend only recovery before submitting ordinary feedback, retaining its eligible request outside the native queue. A burst of non-replacing ordinary calls advances the tracked tail; recovery waits until that tail settles, so messages not explicitly replaced receive their established lifetime and order.
- Recovery never enters the native queue behind another entry. After tail settlement and a safe frame boundary, ask the dashboard to authoritatively revalidate the candidate, then recheck request identity, messenger, tail generation and live caller authority before submission. An intervening ordinary call defers it again. Failed automatic revalidation remains silent/unknown and waits for a later established trigger; it does not loop. All current application Snackbar submissions use this helper; retain that invariant for this feature.
- Only a known current recovery head may be closed, idempotently. Recovery-specific cancellation must never call `close()` on a queued controller or clear unrelated messages; deliberate ordinary replacement and explicit global clearing retain their separate policies. Wait for an outgoing recovery's native removal before submitting a replacement recovery. Native `closed` reason plus the captured programmatic interruption/invalidation cause distinguish user close/swipe from temporary hiding; a late close callback cannot dismiss a replacement request. Retain the outgoing removal barrier even after its request is revoked.
- Explicit close/swipe informs dashboard visit suppression and removes that request. Ordinary displacement does neither: after all ordinary feedback finishes, the same undismissed candidate can reappear following authoritative validation. Action activation removes the request and uses the dashboard's separate single-flight latch. Neither hiding, dismissal nor cancellation writes draft state or consumes a navigation nonce.
- Route departure/cover, logout, account or owner replacement and disposal cancel pending/visible recovery and revoke all captured callbacks. Returning to a retained dashboard may offer an undismissed valid candidate after a fresh lookup; explicit dismissal still suppresses the candidate for that retained visit. A different candidate replaces the old request independently, never inheriting its dismissal or completion authority.
- Separate ordinary replacement from explicit global invalidation inside this helper. `showSnackBar(replaceCurrent: true)` must not call the public recovery-invalidating `clearAppSnackBars` path. Suspend recovery, retain its owned request, remove current/queued ordinary feedback using the existing native clearing operations, invalidate the discarded ordinary-tail generation, and register the replacement as the new tail. Pending and previously visible recovery both remain eligible for authoritative resumption after that tail settles. Replacements still discard older ordinary entries; subsequent non-replacing calls queue normally, and later replacements discard those too. No second queue or state machine is needed.
- Direct `clearAppSnackBars()` remains explicitly global: revoke the owned pending/visible recovery request and ordinary-tail generation before clearing. This does not record user dismissal or delete durable draft/nonce data, but canceled requests and discarded queue callbacks cannot reschedule recovery; only a later established dashboard trigger may create a freshly validated request. Both paths fence old completion callbacks. Do not wait on discarded queued controllers' `closed` futures: Flutter's `clearSnackBars` drops queued entries without completing them. Never close a queued recovery controller; normal interruption closes only the known owned head, while explicit native global clearing retains its existing semantics.
- Current caller audit: `FavouriteButton._handlePressed` directly clears before its asynchronous write to revoke the previous Undo immediately, then uses `replaceCurrent` for successful add feedback. Preserve both intentional operations and the existing favourite regressions. Favourite controls occur on public content surfaces, not the Admin Dashboard/editor; navigating to such a surface revokes dashboard recovery presentation. A still-mounted public caller could also intentionally clear the global messenger, so direct clearing must remain global even if Admin is current. It revokes presentation, not durable recovery or visit dismissal. Do not reinterpret or refactor these callers.
- Handle messenger replacement, absent messenger and show failure with existing diagnostics and no retained stale context. Deferral/cancellation callbacks must not look up disposed inherited widgets. Ordinary Flutter errors/assertions remain visible.

Rejected alternatives: a huge duration is not true persistence; global clear would destroy unrelated messages; closing an arbitrary queued controller violates Flutter's contract; local messengers alone would strand global errors behind an unregistered dashboard Scaffold. No general priority queue, banner or third-party package is warranted.

### A3. Execution-correlated manual refresh receipts

Preserve `refreshSubmissions()`, `refreshIgnoredSources()` and `refreshAfterEditorChange()`. Reuse the implemented `startSelectedLaneRefresh()`, which captures the selected lane and attempts its existing admission exactly once. Refusal returns null; admission returns an immutable receipt whose `settled` Future describes that exact execution after safe settlement. No new command, repository request or refresh coordinator is introduced.

Capture terminal read snapshots privately in `_observe` before public callbacks, extending the existing execution witness already used for mutation. At `_settle`, classify the captured terminal snapshot as success, expected Result error, or handled unexpected error; use explicit revoked and abnormal categories for disposed/skipped or no-normal-terminal execution. Complete the receipt once only after the existing safe-settlement boundary. Never infer outcome from rows, Future completion, mutable latest snapshots or absence of a thrown exception. An assertion is abnormal execution metadata, not a fabricated domain error; keep its original fail-loud route and show no fabricated normal failure. Nonterminating work stays pending. Retain command resources/reporting until physical settlement after disposal. A UI revocation can happen independently of ViewModel disposal and must not cancel or reclassify live remote work.

Both manual entry points reuse the existing Dashboard manual-refresh presentation owner and the admitted receipt. After admission, keep the Dashboard AppBar visible, hide the entire filter bar and replace the visible list, empty state or error placeholders with one `EmptyView.loading` displaying `Caricamento in corso`. Use SyncScreen's loading presentation as the visual reference without navigating to `/sync`. Show one accessible secondary action with the exact visible label `Annulla`. Its accessibility description must explain that it dismisses the wait while the admitted update may continue. Keep this action available for as long as the presentation is visible, including when the read never settles; introduce no timer, artificial timeout or execution cancellation.

Center loading within the available Dashboard content region using layout constraints, including when refresh starts from an already-scrolled list. Do not use a fixed screen offset. Hidden content must not remain visible, interactive, keyboard-focusable or exposed through accessibility traversal. Preserve retained data, selected filter and relevant scroll position where practical; preserving every mounted widget or element identity is not a requirement. Keep the existing NestedScrollView and scroll ownership unless a demonstrated constraint requires a focused adjustment.

Preserve pull gestures and compatible depth-1 scroll notifications. The callback returns immediately on refused admission and otherwise awaits its own receipt's safe settlement, even if presentation authority is revoked first. Display no second native pull spinner. The inspected local Flutter 3.47.5 SDK supports `RefreshIndicator.noSpinner`; it is an implementation candidate, not a normative requirement, and must be rechecked against the implementation SDK. Reuse existing presentation ownership and remove toolbar-specific state if redundant. Refusal creates no loading or result feedback, duplicate request or join of existing work. Selected-lane admission remains authoritative; the other lane remains independently admissible after selection changes.

Capture route/currentness, auth generation, ViewModel identity, selected source and a selection revision before admission, including synchronous reentrant notifications. Any selection change, including away-and-back, revokes its presentation; route cover/departure does likewise. Accepted read data may still commit under normal ViewModel authority. Old completion cannot reset filters, show an error, clear a newer progress owner or touch a replacement widget. Safe settlement or presentation revocation restores normal filters and selected content. Revocation does not cancel or reclassify accepted physical work. Initial, retry, filter-triggered, editor-return and reactivation reads do not acquire this manual-refresh presentation or manual Snackbar side effects.

Accepted success ends progress quietly. Expected and handled unexpected failure show one custom error Snackbar under live authority using the established SyncScreen wording, `Si è verificato un errore durante l'aggiornamento dei contenuti`, and `SnackBarType.error`. The command remains the sole unexpected-error reporter. Success restores normal content without a success notification. After failure, retained content and selection become available again when loading ends; the existing authorized error Snackbar and sole command reporting ownership remain unchanged. Recovery eligibility lookup remains independent of the remote outcome and cannot gate read settlement.

`Annulla` synchronously revokes only the exact manual-refresh presentation token and its feedback authority, then restores filters, retained content, interaction, keyboard focus eligibility, accessibility traversal and relevant scroll state without changing the current selection. A callback from an obsolete action cannot dismiss a newer presentation. Do not use broad route, account or recovery revocation for this action: recovery Snackbar state, lookup authority, route generations and command ownership remain unchanged. Physical reads, private terminal snapshots and the admitted receipt remain untouched; the pull callback must continue awaiting its own execution's safe settlement. Eventual data publication follows normal ViewModel ownership, while the dismissed execution cannot recreate loading, clear newer progress or show obsolete success/error feedback. The pending lane remains single-flight; the independent lane remains available through normal authorized admission after controls are restored.

## Risks / Trade-offs

- Global messenger queue ownership → Test pending, visible, preempted, closed and replaced states deterministically. Native close is safe only for the tracked current persistent entry. No arbitrary queue deletion.
- Persistent message competes with important feedback → Ordinary helper calls temporarily suspend recovery; after the ordinary tail settles, authoritative validation can restore the undismissed candidate. Explicit close/swipe alone records dismissal; all authority transitions revoke old callbacks without deleting intent.
- Route remains mounted underneath an editor or dialog → Current-route checks plus route-generation invalidation, not mounted alone; test covering and return, stale callbacks and A→B→A.
- Late command terminal callbacks race a new execution → Capture each read terminal privately and publish its immutable receipt only at safe settlement; keep existing reactivation and disposal harness assertions.
- Shared action layout fix could affect unrelated notifications → Limit change to guaranteeing existing action placement and native close space; preserve colors, finite timeout and default queue tests at wide/narrow and large text sizes.
- Source inspection does not prove stack/runtime behavior → Actual-router tests are acceptance gates; planning validation is not runtime validation. Do not fix unrelated analyzer baselines.

## Implementation reconciliation

- The dashboard captures route URI as well as Navigator route identity and generations, so a routing change revokes callbacks before a Navigator frame updates currentness. Explicit Back has a synchronous one-navigation latch; system Back retains platform behavior.
- Recovery distinguishes pre-navigation revalidation, admission denial, an observed editor visit and actual Dashboard return. One Dashboard-owned visit token records the expected editor location and a return callback. The existing route listener uses the effective top router URI, observes the Dashboard genuinely covered by that editor, then defers return reconciliation until a frame boundary. It rechecks actual Dashboard currentness, the top Dashboard route, current owner/account authority and the exact visit token, consuming the marker synchronously before any async reconciliation. Both pop and declarative `goNamed(adminDashboard)` finalize once; a declarative move to another editor does not finalize while Dashboard remains covered. R1 denial releases its matching reservation without pretending that an editor visit occurred. The existing public initialized activation plus a fresh exact candidate lookup still solely qualify success suppression. The same narrow marker supplies ordinary editor-return refresh, which shared the independently reproduced missing-refresh defect; ordinary return eligibility uses the existing route lookup, while recovery return performs its own one recheck. Push Futures remain awaited for their existing error propagation but have no return-time effects; neither a pending declarative replacement Future nor a late pop completion can strand or double-finalize the visit. No observer, coordinator or cross-screen activation protocol was added.
- The original delivery used separate toolbar-overlay and native-pull presentations. The final corrective implementation in PR #40 must use the shared A3 presentation and presentation-only `Annulla` action. Existing execution receipts, private settlement and normal ViewModel publication remain authoritative. Implementation and verification status is tracked in section 8 of tasks.md; this design does not claim device acceptance.
- The helper retains one persistent request outside the native queue, plus native ordinary-tail and outgoing-removal barriers qualified by messenger identity. Ordinary replacement suspends that request; explicit global clearing revokes it while preserving any same-messenger outgoing-removal barrier. A helper-owned global-clear token also fences dashboard eligibility work before it registers a persistent request. No second notification queue or persistence state is introduced.

The route visit owns ephemeral presentation state in the existing Dashboard State. Keeping that state with its route lifecycle avoids another state owner. The corrective A3 implementation retains the list and filter subtree offstage while one bounded loading surface keeps its own AppBar available. Exact-token dismissal restores that subtree without changing read settlement or recovery authority; section 8 of tasks.md records automated evidence and pending acceptance. Router configuration/Login, editor activation, persistence implementation, dependencies and backend contracts remain unchanged; R1 extends the existing route admission policy only to acknowledge each recovery rejection. Focused real-store tests extend navigation nonce replacement and compare-and-clear coverage.
