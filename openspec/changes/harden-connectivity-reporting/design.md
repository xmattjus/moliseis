# Design

## Context

Remote `main` in `xmattjus/moliseis` resolved to `a872161cc9812f6758d8febe5dc1a658263cb383`, the same commit cited by [TASK-46](https://app.notion.com/p/41a1b5e75aa781f387e2ec491656957a). A clean dedicated checkout supplied the evidence below. Flutter is pinned to 3.47.5 in the manifest, lockfile and CI. The installed Flutter checkout has that exact tag and its bundled Dart binary reports 3.13.4. The lockfile resolves `sentry`, `sentry_flutter` and `sentry_supabase` to 10.0.0-rc.2 and `functions_client` to 2.7.1.

TASK-41 established ownership by propagation path. TASK-42 retained a centralized remote allowlist, isolated app envelopes and independent automatic-event projection. The canonical `application-observability` scenarios already distinguish a terminal diagnostic from a capture and keep submission independent of sync ownership. The delta adds a cause-specific rule for three existing owners. The Admin exact-receipt contract in `admin-submission-save-idempotency` and public submission orchestration remain applicable. No conflicting canonical requirement was found.

### From failure to transport

1. A producer supplies a typed `LogEvent` and separately attaches the available throwable and stack to `Logger.log`. The sealed taxonomy defines names, levels and diagnostic data. Propagation determines which producer owns a terminal failure. A returned failure, trace completion or later UI observation confers no additional ownership.
2. `AppLogger.log` applies `minLevel` to both destinations. In Debug, an injected Talker receives the original error, available stack and local `event.data` plus `extra`. Sink failures are isolated. Remote work requires an active reporting flag and a level above debug, even without Talker.
3. `AppLogger._remoteDiagnostic` selects the reviewed event families, capture predicate and allowed fields. The default keeps a new event local. An allowed event adds an app breadcrumb. A true report decision additionally calls `_capture`, which constructs a synthetic exception event and uses `Sentry.captureEvent`. Breadcrumbs can exist in scope without any new event envelope.
4. For these three families the report has an `UploadDiagnosticFailure` exception, bounded cause label, safe source frames when available, `app_diagnostic` and `upload_diagnostic` contexts and the current approved breadcrumb. Scope isolation clears ambient context and attachments for this capture. A private per-capture hint carries the approved copy across SDK scope application and processor enrichment. `AppLogger.beforeSend` reconstructs the final event with approved data, restricted correlation/environment data and attachment cleanup before envelope serialization. This second field boundary protects against enrichment after the first projection.
5. SDK automatic Dart errors enter through SDK integrations, bypass the app decision and reach the separate automatic projection/fallback in `beforeSend`. Native SDK reporting can bypass Dart entirely. In `lib/main.dart`, console breadcrumbs and default PII are disabled, Supabase independent error capture is disabled, and streaming traces and Replay retain their own controls. Existing startup consent, forwarding flag, opt-out close and deferred runtime opt-in continue to own their respective gates.

In both repositories the installed Functions client catches failed HTTP sends (apart from the explicit request-aborted rethrow) and throws `FunctionsFetchException(details: error)`. Both catch that subtype before `FunctionException`. The shared `recoverSupabaseFunctionsFetchError` returns details if they implement `Exception`, otherwise the wrapper itself. The logged stack comes from catching the wrapper and need not be the inner transport stack. Raw exceptions caught directly carry their catch-site stack. A plain string that says “offline” provides no typed evidence. A typed but unrelated exception recovered from details remains subject to its own policy.

These are **three defects established by static trace**. The baseline producer tests exercise several concrete failures with recording loggers. Their assertions do not reproduce the three erroneous Sentry captures. No new reproducer was run during planning and no production telemetry was inspected.

## Goals / Non-Goals

Change only capture eligibility for recognized, handled connectivity. Preserve result identity and throw paths, registration of the terminal owner, consent, scope isolation, approved breadcrumbs and operational behavior. There is no transport, persistence, SDK, backend or schema migration.

## Decisions

**Retain the centralized allowlist (A).** Reuse the existing `syncFailureCategory(error) == connectivity` classification for a non-null attached cause. Today it recognizes `SocketException`, `TimeoutException` and HTTP `ClientException` by type. Keep the Cloudinary validation/fileRead veto. Apply the same cause decision to public submission and the staged-association override. Ordinary HTTP errors, malformed contracts, unexpected exceptions and opaque wrappers retain their previous eligibility. Missing causes confer no capture in these three branches.

One subtlety matters when sharing the expression. The existing general `report` predicate *also* excludes `AuthRetryableFetchException` with null status. That separate auth rule is absent from the three baseline branches. Factor the non-null, non-connectivity part into a local boolean, use it in those branches and keep the additional auth rule where it already applies. This local expression is the only selected element of B. It preserves the previous decision for all other cause types and avoids three copies of the connectivity check. There is no reason to change producer taxonomy or to infer offline status from strings, HTTP status, the word “transport” or an unknown outcome.

| Option | Ownership, privacy and discoverability | Maintenance, verification and cost |
| --- | --- | --- |
| A. Correct the three branches in the existing switch | Reviewers can see the owner-specific gates next to each bounded projection. New types default local. | Small decision change, existing harness, no dependency or new processing stage. Preserves TASK-41/42. |
| B. Simplify locally | Share the typed cause decision above. Keep the distinct projections and the Admin operation distinction visible. The additional family selection in `_capture` chooses exception representation and contexts, not eligibility. | One named boolean avoids drift. Grouping unrelated events or refactoring capture formatting saves little and expands the regression surface. No additional cleanup task. |
| C. Move policy onto types or enumerate every subtype | Dart already supports and uses sealed classes, destructuring and logical-or patterns here. Exhaustiveness checks case coverage, not ownership, remote field safety, or whether an attached cause is expected. Putting policy in event parts disperses the inventory and couples local diagnostics to transmission. | Each new local type would need an explicit policy or inherit a default. Neither removes the need for allowlists and envelope tests. Additional migration/review cost without a demonstrated runtime or maintenance gain. |
| D. Use official Sentry APIs | Breadcrumbs record scope context. Exception events provide Issue inputs. Structured Logs produce independently queryable records. An event processor or final filter can transform/drop a submitted event, but cannot undo initiation of a redundant capture or infer domain ownership. | Substituting Logs changes investigation and grouping workflows. Adding Logs increases potential ingestion and billing volume, requires explicit consent gating and a separate field review/filter, and duplicates work if Issues are retained. No volume, grouping or cost savings have been measured. No SDK upgrade or integration is justified. |

**SDK evidence.** In the installed RC, `sentry_client.dart::captureEvent` applies scope and event processors, calls `beforeSend`, then samples and transports the event. `Sentry.captureException` exists, but feeding it the original throwable would still require a safe representation and an ownership decision. `telemetry/log/log_capture_pipeline.dart` processes separate log bodies and attributes, adds scope/default attributes and invokes `beforeSendLog`. Filtering a log does not filter an exception event. `beforeBreadcrumb` can filter breadcrumbs, but lacks the producer's business result. These APIs provide the transport mechanisms already needed by the app. None supplies its allowlist. See Sentry's [Flutter Logs](https://docs.sentry.io/platforms/dart/guides/flutter/logs/), [breadcrumbs](https://docs.sentry.io/platforms/dart/guides/flutter/enriching-events/breadcrumbs/) and [event filtering](https://docs.sentry.io/platforms/dart/guides/flutter/configuration/filtering/) documentation.

## Risks / Trade-offs

- **Accidentally testing a label instead of a cause.** The existing `app_logger_test.dart` HTTP matrix pairs even a timeout-labelled event with a generic Exception. Keep it as a synthetic otherwise-reportable control or relabel its intent. Add real typed causes through the producer seams. Plain HTTP and opaque fetch controls catch overly broad suppression.
- **False zero from an idle or disabled SDK.** Use the shared `RecordingSentryTransport` both as an options-level processor and transport with production `beforeSend`. Settle captures, verify an eligible positive control and count app exception events separately from streaming spans. Assert negative breadcrumbs on scope; assert the current causal breadcrumb in each positive serialized report. Isolated app reports intentionally exclude unrelated ambient crumbs.
- **Duplicating unrelated tests.** Existing upload client and token suites cover retries, cancel, response parsing and passive completion. Public repository tests cover all three transport causes, identity, replay, normalized HTTP errors, malformed success and non-Exception details. Admin repository tests cover staged transport loss, rejection, receipt mismatch and replay. Their logging spies establish producer behavior. Existing `app_logger_test`, `sync_reporting_test`, `automatic_error_privacy_test`, `envelope_isolation_test`, `native_enrichment_test`, `run_traced_result_test` and `sdk_boundary_test` cover adjacent policy, transport, trace and ownership controls. Extend the real boundary cases only where capture, breadcrumb and envelope assertions are missing.
- **Overstating evidence.** Host tests can count app attempts and inspect complete serialized test envelopes. They cannot establish actual backend grouping, frequency, production delivery, or native acquisition/privacy. Automatic Dart errors preserve their own projection. Independent native events and automatic scope-attachment limitations remain as accepted in TASK-42.
